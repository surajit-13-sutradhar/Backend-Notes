Error Handling & Fault Tolerance — Interview Notes

1. The Mindset

Errors are not just problems to solve; they are a normal part of building applications. Database queries will sometimes fail, external APIs will time out, users will send bad data, and your business logic will hit unexpected edge cases.

The question is not whether errors will happen, but how you will handle them when they do.

This chapter is about a fault-tolerant mindset: being ready to detect errors, contain them, and recover, rather than about specific tools or frameworks. It's what responsible backend engineers (who own core business logic and every transaction) need in startups, enterprises, and open source alike.

1) Logic errors

Probably the most dangerous type: the code runs fine but produces the wrong result, so nothing crashes and nothing alerts.

  • Example: an e-commerce store accidentally applies a discount twice, producing negative shipping costs. The app doesn't crash but loses money on every order, possibly for weeks or months if nobody is monitoring or reporting it.
  • Common causes: misunderstood requirements (confusing discussions with a client or PM, then shipping untested), incorrectly implemented algorithms (complex discount logic based on purchase history), and unconsidered edge cases or unexpected user behavior.
  • When money, payments, or security are involved, they can silently corrupt data and business results.

2) Database errors

Most backends rely heavily on the database, so these can take down the whole system.

KindDetails
Connection errorsThe app can't talk to the database: network down, database overloaded, or the connection pool exhausted. (A pool keeps a set of open TCP connections so each request doesn't pay the connection-setup cost.) Result: 500s and empty screens.
Constraint violationsAn operation breaks a database rule: inserting a user with an existing email (unique violation), or inserting an order whose customer_id doesn't exist in customers (foreign key violation). Unhandled, they bubble up as a 500.
Query errorsMalformed SQL, e.g., a typo in a table name, or queries too complex that time out.
DeadlocksOperations wait on each other in a circular dependency.
  • Some constraint errors can be reduced with a stronger validation layer, but some (e.g., unique) can't be avoided: only the database knows whether an email is unique. For those, focus on error formatting so the front end can show a friendly message ("this email already exists, try another").

3) External service errors

Payment processors, email providers, object storage (S3), Redis, auth providers (Auth0, Clerk), AI APIs: each dependency is a point of failure you don't control. You can't avoid external dependencies (nobody rebuilds everything from scratch), so expect them to fail and plan for it.

CauseNotes
NetworkConnection timeouts, DNS failures, network partitions. The internet is not perfect.
Authentication errorsThe external service rejects requests: bad credentials, expired tokens, insufficient permissions. Using a provider doesn't make you secure by itself; your own backend can still cause issues, e.g., exposing sensitive user data in logs.
Rate limitingProviders (email, AI, ...) block abnormal request volumes. A bug or a burst of user activity can make you exceed the limit and get 429 Too Many Requests. Handle it with exponential backoff.
Service outagesEven major cloud providers go down (incidents, maintenance). Handle gracefully with fallbacks. Example: if Redis is down, fall back to an in-memory cache or a second Redis node so core functions (payments, order processing) keep working.

4) Input validation errors

Caused by users sending bad data. The validation layer is your first line of defense against bad or malicious input, at the entry point of the backend. These are the easiest errors to expect and handle (unlike external dependencies or logic errors), so make the validation layer robust in any backend.

  • Format: valid email, phone number, date. Be explicit about exactly what format you accept and accept only that.
  • Range: number too high/low, string too long/short, array with fewer than 3 or more than 100 items.
  • Required fields: mandatory fields must be present.
  • Response: typically 400 Bad Request.

5) Configuration errors

These prevent an app from starting or make production behave unexpectedly, often surfacing when moving between development, staging, and production.

Example: you add an OPENAI_API_KEY to your local .env, merge the PR, and forget to add it to production's variables (manual, or from AWS Parameter Store, etc.). The deployment succeeds. What happens next depends on whether you validate configuration at startup:

%%{init: {'theme':'dark'}}%%

  • Validate all required configuration before the server starts. If anything required is missing or corrupt, crash at startup, before serving real users.
  • With blue-green deployments, the old version keeps running until the new one starts successfully, so a fail-fast startup means no downtime.
  • Configuration management is covered in more depth in the next chapter of the series.

3. Prevention: Error Handling Starts Before the Error

Key idea: the best error handling starts before errors happen. Find problems the moment they occur, before they spread and cause damage.

Health checks (proactive error detection)

%%{init: {'theme':'dark'}}%%
flowchart TD
    M["External monitoring tool
pings the health endpoint"] --> H["GET /health"]
    H --> P["Is the server running?
200 means yes"]
    H --> DB["Database checks
connectivity, query performance, data integrity"]
    H --> EX["External service checks
test transactions, test emails, test tokens"]
    H --> CF["Core functionality checks
configuration loaded, caches populated, internal state consistent"]
  • Basic health endpoint (e.g., /health or /status): the important part is the status code. 200 = running; 4xx/5xx = something's wrong. External tools ping it continuously.
  • But "running" isn't enough. Verify the services are actually doing their job:
    • Database: can we connect? Is query performance normal (a query that took 500 ms now takes 4–5 s is a warning)? Is data integrity intact? Run a representative query and track its timing.
    • External services: payment processors (periodic test transactions, so a successful one 5 minutes ago means you're probably fine), email (send test messages to internal addresses), auth (generate test tokens and validate them against the provider's endpoint).
    • Core functionality: configuration loaded (fail with a meaningful message so the operator can fix it), caches populated, internal data structures consistent.

Monitoring and observability (overview)

A big topic covered in a later chapter. The main points:

  • Detect errors quickly, while they happen, with enough context to debug.
  • Don't only track error rates. Track performance metrics (response times, resource usage, throughput) since degradation is often an early sign a service is about to fail.
  • Track errors across all sources: HTTP, database, external services, business logic.
  • Track business metrics too (successful transactions, successful logins). A sudden drop in successful transactions can indicate a technical problem even when error rates look normal.
  • Structured logging (e.g., JSON logs) is easy to parse and add metadata to. Log aggregation tools like Grafana / Loki let you search logs, build dashboards, and store them externally.

4. Philosophies for Handling Errors

1) Immediate error response

Your immediate reaction determines whether an error stays minor or becomes a major failure. It depends on the error type and context.

%%{init: {'theme':'dark'}}%%
flowchart TD
    ER["An error occurs"] --> Q{"Recoverable?"}
    Q -- "Yes: network blips, temporary resource limits" --> RT["Retry with exponential backoff
without adding stress to an already stressed system"]
    Q -- "No" --> CG["Containment and graceful degradation"]
    CG --> C1["Serve cached data"]
    CG --> C2["Disable non-essential features"]
    CG --> C3["Provide alternative functionality or a fallback"]
  • Recoverable errors (e.g., an email provider failing, running out of database connections): retries and exponential backoff work well. Be careful not to overwhelm an already stressed system. Your retry logic shouldn't add more load.
  • Non-recoverable errors: use containment and graceful degradation: switch to cached data, disable non-essential features, offer a fallback, and limit the scope of the damage.

2) Error recovery strategies

  • Automatic recovery handles many errors without human intervention: automatically restart an unresponsive service, clean up corrupted caches, switch to backup systems. Design these carefully, since they can sometimes make things worse. Test to find what works for which service.
  • Manual recovery is necessary when human judgment is required. Document the procedures (so the whole team and new hires know what to do during an incident) and test them, so they work quickly under stress.
  • Data recovery: data is the most important asset (code and services are replaceable). Protect data integrity as a top priority: take backups at key moments, restore from backups, replay transaction logs, use specialized recovery tools.

3) Propagation control

  • Not every error should be handled where it occurs. Sometimes it should propagate up to a level with more context (where you know the business meaning).
  • Keep the bubbling under your control so errors don't spread to other services or shut down the main service.
  • Use exception hierarchies (try/catch in JavaScript and Python): catch low-level exceptions, wrap them with context, and rethrow to higher levels, where you can log the right data, send a meaningful message to the client, or trigger recovery. This leads to global error handling (next section).

4) Error boundaries

Boundaries are the last point where you stop errors from propagating further. In service architectures they prevent an error in one service from affecting others:

  • Use separate processes.
  • Use timeouts to protect service boundaries.
  • Use message queues (e.g., RabbitMQ) for asynchronous communication, so a bug in one service doesn't cause another to fail.

5. Global Error Handling: the Final Safety Net

A mechanism that takes effort to set up once and pays off immediately and long term. It is arguably the most important error handling strategy in a backend.

The architecture

A typical backend has layers: routing → handler → service → repository.

  • Handler: extracts data from the payload (deserialization, validation, binding), then calls a service.
  • Service: orchestrates one or more repository methods.
  • Repository: leaf functions that each do one unit of work, usually one database query (e.g., getUserById).

The pattern

Wherever an error occurs, bubble it up to a single global error-handling middleware, which turns it into the right HTTP response. Middleware has access to all incoming requests and outgoing responses.

  • In languages with exceptions (JavaScript, Python): throw the error and catch it in the middleware.
  • In languages like Go where errors are returned: keep returning the error from repository → service → handler until it reaches the middleware.
  • Use custom error types (available in every language) so the middleware can tell what kind of error it is.

ScenarioWhere it's raisedResponse
POST /books with a name over 500 charactersHandler (validation)400 with the field errors so the user can fix the data

A common HTTP error body has a code (the status code), a message, and optionally an array of field-level errors. An illustrative middleware:

function errorHandler(err, req, res, next) {
  if (err instanceof ValidationError)
    return res.status(400).json({ code: 400, message: "Validation failed", errors: err.fields });
  if (err instanceof UniqueViolationError)
    return res.status(400).json({ code: 400, message: "Book already exists" });
  if (err instanceof NotFoundError)
    return res.status(404).json({ code: 404, message: err.message });

  logger.error({ err, correlationId: req.id });   // full details stay in the logs
  return res.status(500).json({ code: 500, message: "Something went wrong" });
}

(Illustrative sketch, not from the video.) Status-code choices vary by team. For a duplicate resource, many APIs use 409 Conflict rather than 400, and some use 422 or 400 for a foreign key that points at a nonexistent record. What matters is that the mapping is consistent and defined in one place.

Two major advantages

  1. More robust: it doesn't matter which layer an error comes from; the final gateway handles it. Without it, each layer must remember to translate errors. If one repository method forgets to handle a unique violation, the user gets a vague 500 instead of a meaningful message.
  2. Less redundancy: without a central handler, every repository method that runs SQL would need the same checks (is it a unique violation? a foreign key violation? ...), which spreads duplicated, bug-prone logic across the codebase.

6. Security Aspects of Error Handling

1) Don't leak internals in error messages

  • Never pass a raw error message from a lower layer to the client. Database errors can reveal table names, index names, constraint names, and other internals. Malicious users can use these for more advanced attacks (including SQL injection variants).
  • Compromising your users' security is even worse than compromising the platform: it damages trust and goodwill.
  • Keep control of messages: identify the error and write a user-facing message.
  • In the default (fallback) case, return 500 with a generic message ("Something went wrong" / "Internal server error"). If you reached the fallback, you didn't recognize the error, so its message likely contains internal details. Log the details server-side instead.

2) Login errors: prevent user enumeration

Authentication is one of the most targeted modules. Follow security guidance such as the OWASP cheat sheets (they have advice for authentication and many other areas).

ResponseProblem
"A user with this email does not exist"
"Your password is incorrect"		Attackers can try many emails and learn which accounts exist (the message changes to "password is incorrect"), then guess common passwords for those known emails.
"Invalid email or password" for both casesReveals nothing about which part was wrong. Use this.

3) Logging: don't log sensitive data

  • Don't put emails, passwords, API keys, or credit card numbers in logs. Logs seem internal, but big companies produce hundreds of GB of logs a day and use multiple external services to store and analyze them. In many major breaches, the logs leaked and exposed sensitive data.
  • Instead, log the user ID (not the email) and a correlation ID so you have enough context to debug.

7. Key Interview Takeaways

  • Errors are inevitable; the goal is a fault-tolerant mindset: detect, contain, recover.
  • Five error categories: logic (silent and dangerous), database (connection, constraint, query, deadlock), external service (network, auth, rate limit, outage), input validation (easiest to handle), and configuration.
  • Rate-limit errors (429): respond with exponential backoff. Outages: use fallbacks.
  • Validate configuration at startup and fail fast; this avoids runtime 500s and, with blue-green deployments, avoids downtime.
  • The best error handling starts before errors happen: health checks that go beyond "server is up" (database, external services, core functionality) plus monitoring of performance and business metrics, and structured logs.
  • Recoverable errors → retries with backoff (without stressing the system). Non-recoverable → containment and graceful degradation.
  • Prefer automatic recovery where safe; document and test manual procedures; protect data integrity (backups, transaction log replay).
  • Propagation control: wrap low-level errors with context and bubble them up; error boundaries (separate processes, timeouts, message queues) stop errors spreading between services.
  • Global error handler middleware = the final safety net: all layers bubble errors up; one place maps error types to HTTP responses (400 validation, 404 not found, 500 fallback, and so on). It is more robust and removes duplication.
  • Security: don't leak internal details in messages (generic 500 fallback), use the same message for wrong email and wrong password, and never log sensitive data (log user IDs and correlation IDs instead).

8. Possible Interview Questions to Prepare For

  1. Why are logic errors considered the most dangerous? How would you detect them?
  2. What kinds of database errors can occur? How do you handle unique and foreign key violations?
  3. What is a connection pool, and what happens when it's exhausted?
  4. How do you handle an external API that rate-limits you? What is exponential backoff?
  5. What would you do if a critical dependency (e.g., Redis) goes down?
  6. Why should configuration be validated at startup? What happens if it isn't?
  7. What should a health check verify beyond "the server is running"?
  8. Why monitor performance and business metrics, not just error rates?
  9. Recoverable vs non-recoverable errors: how do you respond to each? What is graceful degradation?
  10. What are error boundaries and how do queues, timeouts, and separate processes help?
  11. Explain global error handling. Why is it better than handling errors in each layer?
  12. Which HTTP status codes would you return for validation failures, missing resources, duplicates, and unknown errors?
  13. How could error messages compromise security? How would you design a login error response?
  14. What should and shouldn't go into logs? What is a correlation ID?
