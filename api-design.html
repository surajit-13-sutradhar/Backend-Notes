REST API Design — Interview Notes

1. Why API Design Matters

API design is one of the most important skills for a backend engineer. This chapter focuses on REST APIs (other styles exist, e.g., RPC and GraphQL, but REST is the most widely used standard).

Even experienced developers keep getting confused by the same questions:

  • Should the URI path segment be plural or singular?
  • PATCH or PUT when updating a resource?
  • Which method for a custom action (not fetch/create/update/delete)?
  • Which HTTP status code for which scenario?

Why the confusion exists: the web standards were written when the web looked very different — mostly multi-page applications (MPAs). Today most front ends are single-page applications (SPAs): the browser downloads all the JavaScript on the first request and does routing on the client side.

Goal of the chapter: not to invent new standards, but to extract a consistent set of rules from the existing ones, so you can stop debating "is this RESTful?" and focus on business logic.

2. History — Where REST Comes From

Tim Berners-Lee and the World Wide Web (1990)

Started to share knowledge globally. Within about a year he invented:

  1. URI — Uniform Resource Identifier
  2. HTTP — protocol for client–server communication
  3. HTML — markup language; the "skeleton" of a page
  4. The first web server
  5. The first web browser
  6. The first WYSIWYG HTML editor (built into the browser)

We still use evolved versions of all of these (HTTP/1.1 → 2 → 3).

The problem: the web's user base grew exponentially and the original design had not accounted for that scale. It was heading towards breakdown.

Roy Fielding and the six REST constraints

Roy Fielding (co-founder of the Apache HTTP Server project) proposed constraints to make the web scalable. He later worked with Berners-Lee on the specification of HTTP/1.1, and in 2000 described the web's architectural style in his PhD dissertation, naming it REST — Representational State Transfer. (Reading that dissertation is recommended for backend engineers.)

#ConstraintMeaning
1Client–ServerSeparation of concerns. Client handles UI/UX; server handles data storage and business logic (front end / back end). Each can evolve independently, which improves scalability.
2Uniform InterfaceStandardized way for components to communicate. Has four sub-constraints: resource identification, resource manipulation through representations, self-descriptive messages, and hypermedia as the engine of application state (HATEOAS).
3Layered SystemArchitecture is made of hierarchical layers; each layer only sees the layer immediately below it. Allows load balancers, proxies, etc. to be added without affecting core functionality.
4CacheResponses must be explicitly labeled cacheable or non-cacheable. Clients can cache, which reduces server load and improves response times.
5StatelessEvery request must carry all the information needed to process it; the server stores no client context between requests. Any server behind a load balancer (e.g., round robin) can handle any request.
6Code on Demand (optional)Server can temporarily extend client functionality by sending executable code (e.g., JavaScript). Optional and rarely emphasized.

3. What "Representational State Transfer" Means

  • Representational — a resource (data/object) is exposed in a specific representation. The same resource can have different representations depending on the client: JSON (most popular, e.g., server-to-server), XML, or HTML (e.g., server-to-browser). Example: a user resource with id, name, createdAt can be sent as JSON to an API client or as an HTML page to a browser.
  • State — the current condition/attributes of a resource. Example: a shopping cart's state = items, quantities, and total price.
  • Transfer — the movement of resource representations between client and server using standard HTTP methods (GET, POST, PUT, PATCH, DELETE, ...). Example: a GET for a web page transfers a representation from server to client.
REST = an architectural style where resources are represented in different formats, their state is transferred between client and server through those representations over HTTP, and the whole system follows the six constraints above to stay scalable.

4. URL Anatomy and API Route Structure

A typical website URL

https://www.example.xyz/blog/post?tag=rest&page=2#comments
└──┬──┘ └──────┬──────┘└───┬───┘└────────┬───────┘└───┬───┘
scheme    authority/domain  path     query params   fragment
  • Scheme — http or https (encrypted).
  • Authority — the domain (may include a subdomain).
  • Path — the resource being accessed. The / represents a hierarchical relationship between resources.
  • Query parameters — key/value pairs, mostly used with GET for filters, pagination, etc.
  • Fragment — makes the browser scroll to a section of the page.

A typical API URL (industry convention, not a hard rule)

https://api.example.com/v1/books
└──┬──┘ └──────┬──────┘└┬┘└──┬─┘
scheme  API subdomain  version resource (plural)
  • APIs usually live on an api. subdomain.
  • Versioning is usually done in the route: /v1, /v2, ...

Path segment rules

  1. Resources are always plural nouns — even when fetching a single item: GET /v1/books (list) and GET /v1/books/{id} (single). Never /book/{id}.
  2. Lowercase only — URLs travel through different servers, clients, and operating systems; avoid case-mismatch problems.
  3. No spaces or underscores — use hyphens to separate words. Example slug: "Harry Potter" → harry-potter → /books/harry-potter.
  4. Slash = hierarchy — /books is the collection (level 1); /books/{id} is one item in that collection (level 2).

5. Idempotency and HTTP Methods

Idempotent operation: performing the same action multiple times has the same effect on the server as performing it once. It does not matter whether you call it once or a thousand times — the side effect is the same.

Note: idempotency is about the side effect caused by the client's call, not about whether the response is always identical. A GET /books may return a different list later because someone else created a book, but your call caused no change, so it is still idempotent.

MethodPurposeIdempotent?Why
GETRetrieve dataYesFetching causes no change on the server.
PUTCompletely replace a resource with the client's payload (all fields sent)YesRepeating the same payload leaves the resource in the same state.
PATCHPartially update a resource (only the changed fields sent)YesSetting name to B repeatedly leaves the name as B.
DELETEDelete a resourceYesThe first call deletes it. Later calls return 404 but change nothing further.
POSTCreate a resource, or perform a custom actionNoEach call creates a new resource (new ID) — side effects differ per call.
  • HEAD (fetch headers only) and OPTIONS (e.g., used in CORS preflight to check whether an origin is allowed) also exist, but the five above cover almost all data operations.
  • PUT vs PATCH: people often use them interchangeably, which is tolerable for internal APIs. For public APIs, stick to the semantics so integrators aren't misled. In SPAs with JSON payloads you mostly update a few fields, so PATCH is the common choice.
  • POST is open-ended: whenever an action does not fit fetch / create / update / delete, use POST — this is how custom actions are modeled (e.g., "send email").

  • Design the interface before writing any business logic. It should be intuitive, unambiguous, and follow REST standards.
  • Why follow standards: without them, consumers can only learn your API's behavior by reading your code or by trial and error — lots of room for guesswork, bugs, and sync calls. If most behavior is predictable from the standard, integration effort drops a lot.
  • Start from the UI design. Wireframes show how end users interact with data, linking users → front end → your API → database.
  • Resources = nouns in the requirements (an oversimplified but useful rule of thumb).

Demo domain: a project-management platform (like Jira / Linear)

Nouns found: organizations, projects, users, tasks, tags. The demo uses three tables: organization, project, task. Fields such as id, createdAt, updatedAt are server-managed and are never accepted from the client payload.

Status codes for the CRUD flow

CodeWhen
200 OKSuccessful fetch, update, or other successful operation that did not create a resource.
201 CreatedA new resource was created. Return the new entity in the body.
204 No ContentSuccessful, but there is no body to return (typical for DELETE).
404 Not FoundThe client requested a specific resource (by ID) that doesn't exist, e.g., GET a deleted organization.
Rule of thumb: for a list API with no matching data, return 200 with an empty array ("data": [], "total": 0), not 404. Use 404 only when a specific resource was requested and doesn't exist.

8. List APIs — Pagination, Sorting, Filtering

All controlled via query parameters (a GET has no body).

Pagination

Why: returning all records is expensive. Serializing thousands of records is resource-heavy and adds server delay, and the user perceives that delay in the UI even though they only see 10–20 items at first. Return one portion (page) at a time.

  • limit — number of items per page (default e.g. 10 or 20).
  • page — which page to return (default 1).

Response shape:

{
  "data": [ ... ],
  "total": 5,
  "page": 1,
  "totalPages": 3
}
  • data — the items for this page.
  • total — total count in the database, independent of the current page (useful for UI like "10 of 50").
  • page — the current page number.
  • totalPages — how many pages exist. Front ends can use it to stop infinite scroll when page == totalPages.

Worked example: 5 organizations with limit=2 gives totalPages = 3: page 1 has 2 items, page 2 has 2 items, page 3 has 1 item.

GET /organizations?limit=2&page=1   → org 5, org 4
GET /organizations?limit=2&page=2   → org 3, org 2
GET /organizations?limit=2&page=3   → org 1

Sorting

  • sortBy — the field to sort by (e.g., name, status).
  • sortOrder — asc or desc.
  • Always have a default sort. Without an explicit sort, databases don't guarantee order, so results could differ between calls. Default: createdAt, descending (latest first). If the client sends sortBy but no sortOrder, default the order to descending.
GET /organizations?sortBy=name&sortOrder=asc

Filtering

Accept field names as query parameters and return only matching records; multiple filters can be combined.

GET /organizations?status=archived
GET /organizations?status=active&name=org 1

Sensible defaults

None of these parameters should be required. A bare GET /organizations must work: page=1, a default limit, and a default sort of createdAt desc.

9. Custom Actions

A custom action is an operation that doesn't fit create / read / update / delete. Model it with POST and put the action name at the end of the path:

POST /organizations/{id}/archive
POST /projects/{id}/clone
  • The path still reads as a hierarchy: collection → specific item → action on it.
  • Why not just PATCH status=archived? Archiving triggers server-side work (e.g., handling the organization's projects and tasks, notifying users by email). Setting a field isn't the same as performing the action.
  • Why not simulate "clone" with a client-side create? The client doesn't know what cloning means on the server (clone tasks too? email the owner?). The server owns that logic, so expose an explicit action endpoint.
  • Don't assume POST means 201. archive returns 200 (nothing was created). clone returns 201 (a new project was created). Choose the status code from what actually happened.
  • Custom actions may accept an optional body (e.g., fields to override when cloning).

10. Consistency Across Resources

The same patterns repeat for every resource (organizations, projects, tasks): list, create, get one, update, delete, and custom actions. Once you know the pattern, you can design any number of APIs with it.

  • JSON keys use camelCase — for both request payloads and responses (createdAt, organizationId).
  • Use the same field name for the same concept across all endpoints. If organizations use description, projects must use description, not desc.
  • Use the same route style everywhere. If /organizations is plural, /projects must be too.
  • Why: a front-end engineer integrates one endpoint and then assumes the rest behave the same way. Breaking those assumptions wastes their time and forces them back into the docs.
  • Even if you don't follow the global REST conventions, pick a style and be consistent.

11. Best Practices Checklist

  1. Provide interactive documentation — OpenAPI / Swagger (a playground for testing and a living spec). Plan it from the start and keep it updated.
  2. Be intuitive and consistent — routes, dynamic parameters, custom actions, payloads, naming, and data formats.
  3. Provide sane defaults
    • Lists: default page, limit, sortBy (createdAt), sortOrder (desc).
    • Creates: require only what is absolutely needed. E.g., if status is omitted when creating an organization, default it to active.
  4. Avoid abbreviations (desc for description) — integrators don't have your context.
  5. Design the interface in a separate session, before coding — using Swagger, Insomnia, or Postman, independent of programming language or framework.

12. Key Interview Takeaways

  • REST (Representational State Transfer) is an architectural style from Roy Fielding's 2000 dissertation, built to make the web scalable. Its six constraints are client–server, uniform interface, layered system, cache, stateless, and code on demand (optional).
  • Representation = the format of a resource (JSON/XML/HTML); state = the resource's current data; transfer = moving representations between client and server via HTTP methods.
  • Path rules: plural nouns, lowercase, hyphens (no spaces/underscores), / means hierarchy, version in the route (/v1), commonly on an api. subdomain.
  • Idempotent methods: GET, PUT, PATCH, DELETE. Non-idempotent: POST.
  • PUT replaces the whole resource; PATCH updates part of it. Prefer PATCH for partial updates.
  • POST = create, or any custom action that doesn't fit the CRUD methods (POST /resources/{id}/action).
  • Status codes: 201 for created, 200 for other successes, 204 for successful delete (empty body), 404 for a missing specific resource.
  • Empty list ≠ 404. Return 200 with an empty array.
  • List endpoints should support pagination (page, limit, response with total / totalPages), sorting (sortBy, sortOrder), and filtering — all with server-side defaults.
  • JSON fields use camelCase, and naming must be consistent across every endpoint and resource.
  • Design first, code later: start from the wireframes → resources (nouns) → schema → actions → interface, and document with Swagger / OpenAPI.

13. Possible Interview Questions to Prepare For

  1. What is REST? What do "Representational", "State", and "Transfer" each mean?
  2. What are the six REST constraints? Explain statelessness and why it helps horizontal scaling.
  3. Why should resource names in URLs be plural? What should a URL for a single resource look like?
  4. What does / mean in a REST path? How would you design a slug for a multi-word title?
  5. What is idempotency? Which HTTP methods are idempotent, and why is POST not?
  6. Is DELETE idempotent even though the second call returns 404?
  7. What's the difference between PUT and PATCH? When would you use each?
  8. How would you model an action like "archive an organization" or "send an email" in REST?
  9. When do you return 200 vs 201 vs 204? Can a POST return 200?
  10. When should an API return 404? What should a list endpoint return when nothing matches?
  11. How do you implement pagination, sorting, and filtering in a list API? Why is a default sort necessary?
  12. What does a paginated response usually contain, and how does the client use it?
  13. Why should APIs use sensible defaults and consistent naming (camelCase, same field names across resources)?
  14. How do you version an API? Where does the version go?
  15. Walk through how you'd approach designing the API for a new product before writing any code.
