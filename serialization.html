Serialization & Deserialization — Interview Notes

1. The Core Problem

A client (e.g., a JavaScript app — React/Angular/Vue) and a server (e.g., a Rust app) communicate over a network (HTTP, gRPC, WebSocket, etc.). This series focuses on HTTP / REST, since it's still the most common client-server communication style.

The problem: JavaScript and Rust have completely different data types.

  • JavaScript → dynamic, interpreted
  • Rust → strictly typed, compiled

So how does an object created in JS reach a Rust server and get parsed correctly, and vice versa?

The solution: Both sides agree on a common standard/format for exchanging data.

  • Client: converts its native data (JS object) → common format → sends over network
  • Server: receives common format → converts into its native data (Rust struct) → does business logic
  • Server: converts response data → common format → sends back
  • Client: receives common format → converts back into JS object → renders UI

2. Definition

Serialization = converting data from a native/language-specific format into a common, transmittable/storable format.
Deserialization = converting data from that common format back into a native/language-specific format.

Purpose: make data language-agnostic and domain-agnostic, so systems built in different languages/environments can understand each other — used both for:

  • Transmission (client ↔ server over network)
  • Storage (e.g., config files, logs, databases)

3. Where This Fits (OSI Model — high level only)

  • Not necessary to master the OSI model in depth for backend engineering, but good to know it exists.
  • Data goes: Application Layer → ... → Physical Layer (eventually becomes bits: 0s and 1s transmitted as electrical/optical signals) and back up the stack on the receiving end.
  • Mental model for a backend engineer:
    • At the application layer, your data is in a serialized format (e.g., JSON).
    • Everything below that (data frames, IP packets, bits) is not your concern — it's handled by lower OSI layers/network stack.
    • On the receiving end, before the server application code touches it, the data is reassembled back into JSON.

4. Types of Serialization Standards

CategoryFormatsNotes
Text-basedJSON, XML, YAMLHuman-readable
BinaryProtobuf (Protocol Buffers), Avro, etc.Not human-readable, more compact/efficient
  • JSON is used ~80% of the time for client-server (HTTP/REST) communication — the focus of this note.
  • XML/YAML are text-based too but less common for REST APIs (more common in configs).
  • Binary formats (Protobuf, Avro) are common in RPC systems like gRPC, not typically raw HTTP/REST.

5. JSON (JavaScript Object Notation)

  • Name comes from its resemblance to a JS object literal, but it's language-independent — used everywhere:
    • REST API request/response bodies
    • Configuration files
    • Log files (structured logging)

Rules of JSON syntax

  1. Enclosed in { } (opening and closing braces).
  2. Keys must be strings, wrapped in double quotes ("key") — no other data type allowed as a key.
  3. Values can be:
    • String
    • Number
    • Boolean
    • Array
    • Object (nested — follows the same rules recursively)
    • null

Example

{
  "name": "John",
  "age": 30,
  "isActive": true,
  "address": {
    "country": "India",
    "phoneNumber": 3456
  },
  "tags": ["admin", "user"]
}

Note: nested objects (address) follow the exact same rules — keys as quoted strings, values of any valid JSON type.

6. End-to-End Flow (Demo Recap)

Example: POST /api/books

Request body (client → server), serialized as JSON:

{
  "id": 1,
  "title": "Some Book Title",
  "author": "Some Author"
}

Flow:

  1. Client (JS) constructs a JS object.
  2. Client serializes it into a JSON string and sends it in the HTTP request body.
  3. Server (e.g., Rust) receives raw bytes → reconstructed into JSON at the application layer → deserializes JSON into its native type (e.g., a Rust struct).
  4. Server performs business logic (e.g., saves book, assigns ID).
  5. Server serializes its response data (e.g., a struct or list of structs) back into JSON.

Response body (server → client):

{
  "books": [
    { "id": 1, "title": "Some Book Title", "author": "Some Author" }
  ]
}
  1. Client receives JSON → deserializes into a JS object/array → uses it to render UI.

7. Key Interview Takeaways

  • Serialization/Deserialization = converting data to/from a common format so that systems in different languages/environments can exchange and understand data — used for both network transmission and storage.
  • It solves the fundamental problem: different languages have different type systems (e.g., JS dynamic types vs. Rust's strict compiled types).
  • JSON is the dominant serialization format for REST/HTTP APIs (~80% usage) due to being simple, human-readable, and lightweight.
  • Two broad categories of serialization standards:
    • Text-based: JSON, XML, YAML
    • Binary: Protobuf, Avro (used in gRPC and other RPC-style/high-performance systems)
  • As a backend engineer, you don't need to worry about the lower OSI layers (packets, frames, bits) — your responsibility starts and ends at the application layer, where data exists as JSON (or whatever the agreed format is).
  • JSON structural rules:
    • Keys → always double-quoted strings
    • Values → string, number, boolean, array, object (nested), or null
  • The concept itself is simple — the "trick" is recognizing serialization/deserialization as the general pattern underlying all cross-language/cross-system data exchange, not just something JSON-specific.

8. Possible Interview Questions to Prepare For

  1. What is serialization and deserialization, and why is it needed?
  2. Why is JSON so widely used for REST APIs compared to XML or YAML?
  3. What's the difference between text-based and binary serialization formats? When would you choose one over the other?
  4. How does a strongly-typed language like Rust/Java handle deserializing loosely-typed JSON data?
  5. Where does serialization fit into the OSI model / network stack?
  6. What are some drawbacks of JSON (e.g., no native date type, larger payload size vs. binary formats like Protobuf)?
  7. Name some binary serialization formats and where they're typically used (e.g., Protobuf with gRPC).
