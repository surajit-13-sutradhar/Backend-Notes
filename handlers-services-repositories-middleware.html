Handlers, Services, Repositories, Middleware & Request Context — Interview Notes

Three closely related topics covered together: the Handler/Service/Repository pattern, Middleware, and Request Context. All three describe how a single HTTP request flows through — and is organized inside — a backend server.

1. The Request Lifecycle Inside the Server

We've already covered the external request lifecycle (client → server over HTTP). This chapter covers what happens inside the server, from the moment the OS forwards the request to a listening port, until a response is sent back.

There's no hard rule that responsibilities must be split into three layers — a single handler could do everything. This is a design pattern adopted for scalability, maintainability, and easier debugging.

2. Handler / Controller Layer

Every handler typically receives two objects by default from the runtime/framework (Go, Node.js/Express, Python, etc. all follow this pattern):

  • A request object — to extract data from.
  • A response object — to send data / set headers back to the client.

You don't create these yourself — the language runtime or framework provides them on every handler invocation.

Responsibilities of the Handler/Controller, in order:

  1. Extract data from the request — depending on the HTTP method:
    • GET → query params
    • POST / PUT / PATCH / DELETE → request body (and/or path params)
  2. Deserialize / Bind the JSON payload into the language's native data format:
    • Go → a struct
    • Python → a dictionary or class
    • Rust → a struct
    • Node.js — often handled upstream by middleware (e.g. express.json() / body-parser) before it even reaches the handler, since JS has native JSON support.
    This step is commonly called binding. If deserialization fails, the server responds immediately with 400 Bad Request and terminates — it does not proceed further.
  3. Validation & Transformation (covered in the previous chapter) — validate all incoming data (path params, query params, body) as specifically as possible, then optionally transform it:
    • Example: a GET /books?sort=name|date endpoint. Query params should ideally always be optional — a good API design habit. If the client sends no sort value, validation still passes (since it's optional), and the transformation step can set a sensible default (e.g., sort=date) so downstream layers don't need extra conditional branching.
  4. Call the Service layer, passing the validated/transformed data plus any contextual info the service might need (e.g., authenticated user ID, permissions).
  5. Send the response — after the service layer returns, the controller decides the appropriate status code (200-series for success, 400 for client errors, 500 for server errors) and sends the response body back to the client.
The controller layer is responsible for all HTTP-related concerns: request/response formats, status codes, validation. It effectively controls the data flow between client and server.

3. Service Layer

  • Should not deal with any HTTP-related concerns (status codes, request/response formats). Looking at a service method in isolation, you shouldn't be able to tell it's used behind an API at all.
  • Takes data in, processes it (business logic), returns data out.
  • Can call one or more repository methods for database operations.
  • Can also do things that don't touch the database at all — e.g., a service whose only job is sending an email, which then just returns something like { success: true }.
  • Orchestration: the service layer can combine/merge results from multiple repository calls, make external API calls, send notifications — anything needed to fulfill the business operation for that API call.

4. Repository Layer

  • Sole responsibility: take some data, construct and execute a database query (insert/fetch/update/delete), and return the result.
  • Single Responsibility Principle applies strictly here: a repository method should return one kind of data.
    • ❌ Don't design one method that returns either "all books" or "a single book" based on an optional parameter.
    • ✅ Have a dedicated method for "get all books" and a separate one for "get a single book by ID."

5. Middleware

Middleware functions sit at the boundaries between different execution stages of the request lifecycle — e.g., between the entry point and routing, between routing and the handler, or between the handler and the final response.

What a Middleware Receives

Like a handler, a middleware gets a request object and a response object — but additionally gets a third thing: next, a function.

  • next() passes execution forward to the next middleware (or to routing, or to the handler) in the chain.
  • Because it has access to the response object, a middleware can short-circuit the request and send a response directly — without ever reaching routing or the handler (e.g., failed authentication, CORS rejection, rate limit exceeded).
  • All middleware is optional — you can skip straight from routing to the handler with zero middleware in between if your app doesn't need any.

Why Use Middleware? (Same reason we use functions)

  • Avoid code duplication — common operations (security, logging, auth, rate limiting) that need to run for every request/endpoint are written once, not copy-pasted into every handler.
  • A large backend can have hundreds/thousands of endpoints/handlers — middleware centralizes cross-cutting concerns instead of repeating them per-handler.

⚠️ Order of Middleware Matters

Execution flows linearly, one middleware calling next() to hand off to the next. Where you place a middleware in the chain determines what it can and cannot see/affect.

Common Middleware Examples

MiddlewarePurposeTypical Position
CORSChecks request Origin; if it matches an allowed frontend origin, adds headers permitting the browser to allow the response (same-origin policy workaround)Very early — reject/allow before wasting further resources
Security HeadersAdds headers like Content-Security-Policy for every requestEarly

Rate LimitingTracks requests per IP/client within a time window; if the threshold is exceeded (e.g., "30 requests / 2 seconds") → 429 Too Many RequestsEarly, before handler

Global Error HandlingCatches unstructured errors from anywhere in the app, classifies as client (400) or server (500) error, returns a properly structured error responseLast — must run after everything else so it can catch errors from any prior stage
CompressionCompresses large JSON responses (e.g., gzip) for transit; browsers decompress automaticallyNear the response-sending end
Data Parsing / ValidationCan delegate serialization/deserialization or validation/transformation to a shared middleware instead of repeating it per-handler (implementation choice, depends on codebase conventions)Before the handler
Why Global Error Handling must be last: errors can occur at any point in the chain — in a middleware, the handler, or the service layer. Only a middleware positioned at the very end of the chain can guarantee it has a chance to intercept and format any error that occurred anywhere upstream before the response is finally sent.

Typical ordering in many real backends: CORS → Logging → Authentication → (business logic: Handler/Service/Repository) → Global Error Handling (last).

6. Request Context

Request Context = a storage/state scoped to a single request, accessible across all middleware and handler boundaries for that request's lifetime. Implementation details vary by language/framework, but the concept is universal (Go's context.Context, Node's request-scoped objects, Python frameworks' context objects, etc.).

Typically a simple key-value store, letting different execution stages (middlewares, handlers) share data without tightly coupling them together (i.e., without having to pass values explicitly through every function signature).

Common Use Cases

  1. Passing authenticated user info downstream. The authentication middleware verifies the token/credentials, extracts userId and role, and stores them in the request context. Later, the handler reads userId from the context — not from the client payload — when inserting a record (e.g., a new book row tied to a user).
    Why not trust a userId sent by the client? A malicious client could send someone else's user ID in the payload to perform unauthorized operations on their behalf. Always derive identity from verified authentication data stored in the context, not from client-supplied fields.
  2. Request tracing / correlation IDs. An early middleware generates a unique ID (e.g., a UUID) and stores it in the context as the requestId. This ID can then be used in logs and forwarded to downstream microservice calls (e.g., in an X-Request-Id header), making it possible to trace a single request's full path across services when debugging or auditing.
  3. Cancellation / abort signals and deadlines. Contexts can carry cancellation signals and timeouts so that downstream/external service calls don't hang indefinitely if the parent request should be aborted.

7. Key Interview Takeaways

  • Handler/Controller: extracts & deserializes ("binds") request data, runs validation/transformation, calls the service layer, and owns the HTTP response (status code + body). All HTTP concerns live here.
  • Service: pure business logic, no HTTP awareness; orchestrates one or more repository calls and/or external actions (emails, webhooks, other API calls).
  • Repository: single-responsibility DB access — one method, one kind of operation/return type. Never overload a method to conditionally return different shapes of data.
  • This three-layer split isn't mandatory — it's a design pattern for scalability, maintainability, and testability.
  • Middleware = functions that run at boundaries in the request lifecycle, receiving (request, response, next). They exist to eliminate duplicated cross-cutting logic (security, logging, auth, rate limiting) across many handlers.
  • Middleware can short-circuit the request (send a response directly) without reaching the handler — e.g., failed CORS check, failed auth, rate limit exceeded.
  • Order of middleware matters — e.g., Global Error Handling middleware must be last so it can catch errors from every prior stage.
  • Request Context = a per-request shared key-value state accessible to all middleware/handlers in that request's lifecycle, used to decouple components (e.g., passing authenticated userId/role, request IDs for tracing, or cancellation signals) without threading parameters through every function call explicitly.
  • Security principle: derive user identity/permissions from the authenticated context (set by auth middleware), never trust identity fields sent directly by the client in the request body.

8. Possible Interview Questions to Prepare For

  1. What are the responsibilities of the Handler/Controller, Service, and Repository layers, and how are they different?
  2. Why should the service layer have no knowledge of HTTP-specific concepts like status codes?
  3. Why should a repository method only return one kind/shape of data?
  4. What is middleware, and what three things does it typically receive?
  5. How does the next() function work, and what happens if a middleware doesn't call it?
  6. Why must global error-handling middleware be placed last in the chain?
  7. Give examples of common middleware and explain why each is implemented as middleware rather than inline in a handler.
  8. What is a request context, and what problem does it solve?
  9. Why should you take the user ID from the request context (set during authentication) instead of from the client-supplied request body?
  10. How would you implement request tracing across microservices using request context?
