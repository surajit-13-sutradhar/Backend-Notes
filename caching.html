Caching — Interview Notes

1. What Is Caching?

One sentence: caching is a mechanism to decrease the time and effort it takes to do some work.
Technical definition: keeping a subset of some primary data in a location that is faster and cheaper to access, chosen by how often the data is used and how likely it is to be used again soon.
  • It's a subset, not a copy of everything. The fast storage is more expensive and smaller than the primary storage, so you can't cache everything.
  • It is a huge factor in high-performance applications, especially ones tracking latency in the tens of milliseconds or microseconds.
  • Cache hit = the data you're looking for is in the cache. Cache miss = it isn't, so you go to the primary source.
%%{init: {'theme':'dark'}}%%
flowchart TD
    R["Request"] --> C{"In cache?"}
    C -- "Yes: cache hit" --> H["Return cached result, fast"]
    C -- "No: cache miss" --> S["Compute or fetch from the primary source"]
    S --> W["Store the result in the cache"]
    W --> H2["Return the result"]

When caching comes into play

Two common scenarios, seen in every example below:

  1. You want to avoid doing heavy computation again and again.
  2. You want to avoid sending/fetching large amounts of data to many users repeatedly.

2. Real-World Examples

Google Search

  • Answering a query involves crawling, indexing, and ranking billions of pages, which is computationally expensive.
  • Queries like "what is the weather today" are searched millions of times a day. Recomputing each time would mean huge latency and server load.
  • Google uses a distributed in-memory caching system (cache servers spread across the world). It checks the cache first: a hit returns instantly; a miss runs the full workflow, then caches the result for the next user.

Netflix

  • Each movie is encoded into several resolutions (1080p, 720p, 480p, ...) and the right one is served based on the device and network speed.
  • Serving terabytes of video to millions of users worldwide with minimal buffering is done with a CDN (content delivery network).
  • Netflix's origin servers hold all the content; edge locations around the world hold a subset, placed close to users to keep latency low. Which subset to cache in each region is decided with trend analysis and ML, since caching everywhere would be far too costly.
  • Not just Netflix: many companies use CDNs for videos, images, and static web assets (JavaScript, HTML, CSS). Platforms like Vercel have an edge network too, serving requests from the region closest to you.
%%{init: {'theme':'dark'}}%%
flowchart TD
    O[("Origin servers
all the content")]
    O --> E1["Edge location, Asia"]
    O --> E2["Edge location, Europe"]
    O --> E3["Edge location, Americas"]
    E1 --> U1["Nearby users

X (Twitter) — trending topics

  • Detecting trends means analyzing millions of tweets in real time with heavy ML on lots of GPUs and terabytes of data. Doing that for every user opening the trending section would crash the servers.
  • Trends don't change every few seconds (a topic like an ongoing election stays for hours or days), so it is safe to compute every few minutes and cache the result in an in-memory key–value store (like Redis). Users then get it instantly.
  • (The exact algorithm and refresh interval are not public; this is the general idea.)

4. Network-Level Caching

CDN — Content Delivery Network

Cache content on servers geographically close to the user (edge nodes / edge servers) to minimize latency and reduce load on the origin server.

%%{init: {'theme':'dark'}}%%
sequenceDiagram
    participant B as Browser
    participant D as CDN DNS
    participant E as Edge server in the nearest PoP
    participant O as Origin server
    B->>D: Resolve the domain name
    D-->>B: IP of the nearest point of presence
    B->>E: Request the resource
    alt Cache hit
        E-->>B: Cached resource
    else Cache miss
        E->>O: Fetch the resource
        O-->>E: Resource
        E-->>B: Resource, cached with a TTL
    end
  1. The user requests a resource (image, video, web page) by URL. The browser sends a DNS query to resolve the domain into an IP.
  2. The CDN's DNS routes the request to the nearest PoP (Point of Presence) — a region containing multiple edge servers. Routing considers the user's location and network conditions (e.g., a user on a poor connection may be sent to a PoP that holds lower-quality video). A user in New York is routed to a PoP near New York.
  3. The edge server checks its cache. Hit → serve immediately. Miss → fetch from the origin server, serve it, and cache it.

TTL (time to live): each cached item gets a lifetime (e.g., a few hours). After it expires, the next request fetches fresh content from the origin, which handles new versions and regional changes.

DNS caching

DNS resolves a domain (example.com) to an IP address. Doing the full lookup for every request would be a lot of work for billions of users, so DNS caches heavily at multiple layers.

%%{init: {'theme':'dark'}}%%
sequenceDiagram
    participant U as User device
    participant R as Recursive resolver
    participant Root as Root server
    participant TLD as TLD server for .com
    participant A as Authoritative name server
    U->>R: What is the IP of example.com?
    Note over R: Checks its local cache first. A hit returns immediately
    R->>Root: Query, on a cache miss
    Root-->>R: Referral to the .com TLD server
    R->>TLD: Query
    TLD-->>R: Referral to the authoritative server for example.com
    R->>A: Query
    A-->>R: IP address
    Note over R: Caches the answer for next time
    R-->>U: IP address
  • Recursive resolver — provided by your ISP (e.g., Jio, ACT, Airtel) or a public DNS provider (Google, Cloudflare). It is "recursive" because it keeps going through servers until it finds the IP.
  • Root servers — don't know the IP, but know which servers handle each top-level domain (.com, .in, ...).
  • TLD servers — point to the authoritative name server for the domain.
  • Authoritative name server — holds the real answer (the IP).

Cache layers (a miss at one layer falls through to the next):

%%{init: {'theme':'dark'}}%%
flowchart LR
    A["Browser DNS cache"] -- miss --> B["Operating system DNS cache"]
    B -- miss --> C["Recursive resolver cache"]
    C -- miss --> D["Root, TLD and authoritative servers
full lookup, some of which also cache"]

Operating systems (Windows, macOS, Linux), browsers (Chrome, Firefox), recursive resolvers, and even some authoritative servers keep their own DNS caches. In practice the browser's own cache is usually checked before the OS cache.

5. Hardware-Level Caching

%%{init: {'theme':'dark'}}%%
flowchart TD
    CPU["CPU"] --> L1["L1 cache"]
    L1 --> L2["L2 cache"]
    L2 --> L3["L3 cache
shared between cores"]
    L3 --> RAM["RAM, main memory
fast, volatile, limited capacity"]
    RAM --> DISK["Secondary storage: SSD, HDD, network storage
slower, persistent, large capacity"]
  • CPUs keep L1, L2, and L3 caches for frequently used or soon-to-be-used data. Example: traversing an array sequentially is fast partly because the CPU predicts access and pulls neighboring memory into cache.
  • RAM (Random Access Memory) is the focus for backend work. It's "random access" because any address is reachable directly (electrically) in roughly constant time, unlike a hard disk, where a mechanical head must move.
  • Trade-off: RAM gives up capacity and non-volatility (its data is lost when power is off) in exchange for speed. So it can't replace disk storage.
  • Disk storage is persistent (data stays regardless of power or running programs), and cheaper with far more capacity, but slower.

6. Software-Level Caching: In-Memory Key–Value Stores

Technologies: Redis (and Valkey, its open-source alternative), Memcached, and the managed cloud version AWS ElastiCache.

They're described as in-memory, key–value, NoSQL databases:

  1. In-memory — data lives in RAM, not on disk (unlike PostgreSQL or MySQL), so access is very fast.
  2. Key–value — a simple structure: a key maps to a value (string, number, JSON, list, ...; supported types vary by tool).
  3. NoSQL — no strict schema, tables, or rows, and no SQL joins or aggregations.
  4. For persistence, these tools use secondary storage behind the scenes and reload data into memory on startup. But reads and writes are served from memory.

Usage is simple: use the client library for your language (e.g., node-redis), SET a key with a value, and GET it by key.

SET weather:mumbai "{...json...}" EX 3600   # cache for 1 hour (TTL = 3600 seconds)
GET weather:mumbai                           # cache hit returns the value, miss returns nil
DEL weather:mumbai                           # invalidate manually

7. Caching Strategies

Lazy caching (cache-aside)

Cache only when something is actually requested — no predicting ahead of time.

%%{init: {'theme':'dark'}}%%
sequenceDiagram
    participant C as Client
    participant S as Server
    participant K as Cache
    participant D as Primary storage
    C->>S: Request resource
    S->>K: Check the cache
    alt Cache hit
        K-->>S: Data
    else Cache miss
        S->>D: Fetch the data
        D-->>S: Data
        S->>K: Store the data
    end
    S-->>C: Response
  • Pro: only data that is actually requested is cached.
  • Con: the first request for each item is slow (a miss).

Write-through caching

An update strategy: whenever data is created or changed (POST, PUT, PATCH), update the database and the cache in the same flow.

%%{init: {'theme':'dark'}}%%
sequenceDiagram
    participant C as Client
    participant S as Server
    participant D as Database
    participant K as Cache
    C->>S: Create or update a resource
    S->>D: Write the change
    S->>K: Write the same change
    S-->>C: Response
    Note over K: The cache is always fresh
  • Pro: the cache is always fresh, so you never serve stale data.
  • Con: every write pays extra overhead (two writes).

8. Eviction Policies

RAM is limited (and managed services like ElastiCache have a set limit), so eventually the cache is full. An eviction policy decides which old data to remove to make room for new, more important data.

%%{init: {'theme':'dark'}}%%
flowchart TD
    N["New key arrives"] --> F{"Cache full?"}
    F -- No --> S["Store the key"]
    F -- Yes --> P{"Eviction policy"}
    P -- "No eviction" --> ERR["Error: memory is full"]
    P -- "LRU" --> A["Evict the least recently used key"]
    P -- "LFU" --> B["Evict the least frequently used key"]
    P -- "TTL based" --> T["Evict the key expiring soonest"]
    A --> S
    B --> S
    T --> S

Worked example: the cache holds keys 1–4 and is full, and key 5 arrives.

PolicyHow it decidesExample outcome
No evictionNo policy configured; inserts fail once memory is fullKey 5 gets an error
LRU — Least Recently UsedTracks when each key was last accessed; evicts the oldest accessKeys 1–3 were used today, key 4 yesterday → evict key 4
LFU — Least Frequently UsedTracks how many times each key was accessed; evicts the lowest countAccess counts 5, 10, 6, 23 → evict key 1
TTL basedEvicts the key with the least remaining time to live (closest to expiring anyway)Evict the key expiring soonest

In Redis these are configured as noeviction, allkeys-lru, allkeys-lfu, volatile-ttl, and so on.

9. Backend Use Cases for Redis / In-Memory Caches

1) Database query caching

  • Situation: a query with many joins and aggregations over millions of rows is compute-intensive, and its API is hit very frequently (e.g., a landing page or dashboard), loading the database.
  • Solution: cache the result with a TTL (e.g., 1 hour). Serve from cache when present; otherwise compute once and store it. Update or delete the cached entry when the underlying data changes (invalidation).
  • Amazon: product details, prices, and inventory rarely change but are read by millions of users during a sale. Serving those reads from cache keeps the database free for important work.
  • Social media: user profile data changes rarely but a celebrity's profile may be read millions of times a day. Cache it and invalidate on edit.
  • Rule of thumb: good candidates are read-heavy data with infrequent writes.

2) Session storage

After authentication, a session is created and looked up on every API call. Storing sessions in Redis avoids a database hit per request, since reading from RAM is much faster, and keeps latency and database load low.

%%{init: {'theme':'dark'}}%%
sequenceDiagram
    participant C as Client
    participant S as Server
    participant K as Redis
    C->>S: Login
    S->>K: Store session token with a TTL
    S-->>C: Session token
    C->>S: Later request with the token
    S->>K: Look up the session
    K-->>S: Session data
    S-->>C: Response

3) External API caching

  • Situation: your backend calls an external API (e.g., a weather API). Without caching, every one of your users' requests triggers an external call, which pushes you into rate limits and higher billing.
  • Solution: weather doesn't change every second, so cache the response with a TTL of, say, 1 hour. All requests in that hour use the cached value; after expiry, fetch again and re-cache.
  • Only suitable for data that is not real-time critical.

4) Rate limiting

Rate limiting is usually a middleware that runs before your routes or controllers. It identifies the client (commonly by IP, from the X-Forwarded-For header set by a reverse proxy such as Nginx) and keeps a counter per client in Redis.

%%{init: {'theme':'dark'}}%%
flowchart TD
    R["Incoming request"] --> M["Rate limit middleware
reads the client IP from X-Forwarded-For"]
    M --> I["Increment the counter for that IP in Redis
the counter expires after 1 minute"]
    I --> Q{"Counter above 50?"}
    Q -- Yes --> X["429 Too Many Requests"]
    Q -- No --> N["Pass the request to the route or controller"]

INCR rate:10.12.0.1        # returns the new count
EXPIRE rate:10.12.0.1 60   # set once, when the count is 1, so the window resets after 60 seconds
# if the count is above 50, respond with 429 Too Many Requests
  • Purpose: protect expensive APIs and stop bots or abusive clients (for example, allow 50 requests per minute per IP).
  • Why Redis and not a relational database? A relational database would work, but each request would pay an extra database call (even 20–30 ms matters for latency), and thousands of users making many requests per minute would flood the database with rate-limit traffic. In-memory storage fixes both: lower latency and less database load.

10. Trade-offs to Keep in Mind

  • Cost and capacity: memory is more expensive and smaller than disk, so you cache only a subset of the data.
  • Staleness: cached data may be out of date. Handle it with TTLs, write-through updates, or invalidating on writes.
  • Right data: cache data that is expensive to compute or fetch, read often, and changes rarely. Don't cache everything.
  • Persistence: RAM is volatile. The cache should not be the only home of important data (the primary storage remains the source of truth).

11. Key Interview Takeaways

  • Caching = keeping a subset of data in faster, cheaper-to-access storage to reduce time and effort. A hit is served from the cache; a miss falls back to the primary source.
  • Use it to avoid heavy computation and heavy data transfer (Google search, Netflix, Twitter trends).
  • Three levels: network (CDN, DNS), hardware (CPU caches, RAM), software (Redis, Memcached, ElastiCache).
  • CDN: origin server + edge servers grouped into PoPs; DNS routes users to the nearest PoP; hit → serve, miss → fetch from origin and cache; content expires by TTL.
  • DNS caching happens at multiple layers (browser, OS, recursive resolver, some authoritative servers) to skip the full root → TLD → authoritative lookup.
  • RAM is fast (random access, no mechanical parts) but limited and volatile; disk is slower but persistent and large. In-memory stores trade capacity and durability for speed.
  • Redis and Memcached are in-memory, key–value, NoSQL stores.
  • Lazy caching (cache-aside): load into the cache on a miss. Write-through: update cache and database together, so the cache stays fresh but writes cost more.
  • Eviction policies: no eviction, LRU, LFU, TTL-based.
  • Use cases: DB query results, session storage, external API responses, rate limiting counters.
  • Rate limiting returns 429 Too Many Requests and keeps counters in Redis to avoid latency and database load.
  • Good cache candidates: read-heavy, rarely changing data.

12. Possible Interview Questions to Prepare For

  1. What is caching and why is it used? What are cache hits and misses?
  2. Why cache only a subset of the data instead of everything?
  3. How does a CDN work? What are edge servers and a PoP?
  4. How does DNS resolution work, and where does caching occur along the way?
  5. What is TTL and why do cached items need one?
  6. Why is RAM faster than disk? Why can't RAM just replace disk-based databases?
  7. What is an in-memory key–value store? Name some examples (Redis, Memcached, ElastiCache, Valkey).
  8. Explain lazy caching (cache-aside) vs write-through. What are the trade-offs?
  9. What are eviction policies? Explain LRU, LFU, and TTL-based eviction with an example.
  10. How would you cache an expensive, frequently called database query? How do you keep it consistent when data changes?
  11. Why store sessions in Redis instead of the primary database?
  12. Why would you cache the response from a third-party API?
  13. How would you implement rate limiting with Redis? Which status code do you return, and why not use a relational database?
  14. When should you not cache something?
