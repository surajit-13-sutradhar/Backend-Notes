Full-Text Search & Elasticsearch — Interview Notes

1. The Problem: Why LIKE Stops Working

Imagine it's 2005. You work at a fast-growing e-commerce company with about 5,000 products, and you must build a search API. In a relational database that looks like:

SELECT * FROM products
WHERE name ILIKE '%laptop%' OR description ILIKE '%laptop%';

The % signs match any characters before and after the keyword, so a product matches if the keyword appears in the name or the description. With a few thousand products, it's fast and life is simple.

Then the company grows to millions of products. The query that took ~50 ms now takes ~30 seconds. Customers and managers are frustrated, and there are new requirements:

  1. Speed — results in milliseconds.
  2. Relevance — searching "laptop" should show a MacBook Pro before a laptop bag.
  3. Typo tolerance — customers in a hurry type "lapotp"; results should still be relevant.

This is the story of why search engines like Elasticsearch exist.

2. The Librarian Analogy

Think of your relational database as a librarian who knows where every book is, but has one fatal flaw: to find books about "machine learning" they must check every book on every shelf, one by one. (In database terms, a sequential scan of every row, examining every text field and pattern-matching character by character.)

  • Slow: the time grows with the size of the library, minutes, hours, or days for millions or billions of books.
  • No concept of relevance: a book titled Introduction to Machine Learning and a book that mentions the phrase once on its last page are both just "matches", returned in arbitrary order. The truly relevant result might land at position 1,000 or 10,000.

A LIKE '%term%' pattern with a leading wildcard also can't use a normal B-tree index, which is why it degrades into scanning the whole table.

Around 2005 the information explosion (Google crawling billions of pages, Amazon cataloging millions of products, LinkedIn indexing millions of profiles) made this unacceptable: even 2 seconds of delay hurts conversion, and search must return in milliseconds. The answer came from decades of text-search and information-retrieval research (since the 1960s).

3. The Key Idea: the Inverted Index

Flip the problem. Instead of going through every document to find a term, build an index ahead of time that maps each term → the documents (and positions) where it appears. That's an inverted index.

  • This is what powers Elasticsearch. It is built on Apache Lucene, the underlying inverted-index-based text-search library.
  • Elasticsearch isn't the only tool. Many full-text search tools use Lucene, and even relational databases like PostgreSQL have built-in full-text search.

4. Relevance Scoring

The second big advantage is relevance: results are ranked, not just matched. Elasticsearch scores each matching document using the BM25 algorithm. You don't need to know the math; you do need to know the ideas behind its parameters. (In Elasticsearch, a single entity is called a document, a JSON document, similar to MongoDB.)

FactorMeaning
Term frequencyHow often the term appears in this document. More occurrences → more relevant.
Document frequencyHow common the term is across all documents. Rarer terms are more informative.
Document lengthHow long the document is (a match in a short document counts for more than in a very long one).
Field boostingWhich field matched. A match in the title is more relevant than in the description, which is more relevant than in the content. You can define your own boosts in the query.

Example: searching "machine": Introduction to Machine Learning ranks first (the term is in the title and appears frequently). The Machine Age is second (in the title, but less frequent), and so on.

Queries are written in the Elasticsearch Query DSL, a JSON-based query language with many parameters for different kinds of search. An illustrative example combining field boosting and typo tolerance:

GET /products/_search
{
  "query": {
    "multi_match": {
      "query": "laptop",
      "fields": ["name^3", "description"],   // a match in name counts 3x
      "fuzziness": "AUTO"                    // tolerate small typos
    }
  }
}

5. Typo Tolerance and Type-Ahead

  • Full-text search engines can infer intent despite typos. In the Google-search example, typing "what is treading today" still surfaces "what is trending today". (Whether Google uses Elasticsearch or something proprietary built on Lucene isn't known; the experience is similar.)
  • The same technology builds type-ahead / autocomplete interfaces (as on Amazon).
  • In Elasticsearch, this is typically done with fuzzy matching (matching terms within a small edit distance).

6. Choosing a Tool: PostgreSQL FTS or Elasticsearch?

For a search-like feature in your backend, there are two common options:

OptionWhen it fits
PostgreSQL full-text searchYou already use Postgres and want search without adding new infrastructure.
ElasticsearchYou need rich relevance tuning, typo tolerance, type-ahead, and search at large scale. Also a strong choice if your company already runs Elasticsearch (e.g., for logs).
-- PostgreSQL full-text search (illustrative)
CREATE INDEX idx_reviews_fts ON reviews USING GIN (to_tsvector('english', review));

SELECT id, review, sentiment
FROM reviews
WHERE to_tsvector('english', review) @@ plainto_tsquery('english', 'laptop');

(Added example, not shown in the video.)

The ELK stack

Elasticsearch is also famous in log management: the ELK stack is Elasticsearch + Logstash + Kibana. Elasticsearch is very fast at searching through logs, computing statistics, and visualizing data. If your company already has Elasticsearch for logs, using it for full-text search requirements is a sensible choice instead of Postgres.

7. Demo: Postgres ILIKE vs Elasticsearch

A Next.js prototype compares the same search on both systems. For fairness, both are cloud-hosted in the US-West region, so network distance isn't a major factor: Neon (serverless Postgres) and Elastic Cloud.

Setup

  • Data: a CSV of 50,000 reviews, each with a review and a sentiment (positive or negative).
  • Postgres: a reviews table with id, review (text) and sentiment. A Node.js populate script filters out rows missing either field and inserts in batches of 1,000 (a single huge insert hits limits on the Neon instance).
  • Elasticsearch: a reviews index (deleted and recreated if it already exists), with the mapping review: text and sentiment: keyword, loaded with a bulk insert of all 50,000 records.

text vs keyword field types

  • text — analyzed for full-text search: the value is broken into terms (and normalized) so individual words can be searched and scored.
  • keyword — stored as a single exact value, matched exactly (good for statuses, tags, sentiment labels).

How the demo API works

  • The route streams each system's result to the front end as soon as it's available, so one doesn't delay the other and you can see which is faster.
  • The Postgres side is the classic SELECT ... WHERE review ILIKE '%term%' (case-insensitive, any characters before and after).
  • The Elasticsearch side runs a query-string search over the index with the term lower-cased and wrapped in wildcards, so the match criteria are the same on both sides.

The demo's point is the cost of LIKE-style scanning.

How much should you learn?

  • Database knowledge (working with databases, optimizing them, understanding indexes) is something you must master; it touches almost all of your codebase as a backend engineer.
  • Elasticsearch is a tool to have in your arsenal: know when to use it and adapt examples from the docs. The docs' snippets cover most search use cases. Read deeper only if you need to optimize.

8. Key Interview Takeaways

  • Relational LIKE '%term%' search scans every row, so it gets slower as data grows, and it has no notion of relevance.
  • Search engines solve this with an inverted index: term → documents (and positions), built ahead of time. Lookup replaces scanning.
  • Elasticsearch is built on Apache Lucene. Documents are JSON; queries use a JSON-based Query DSL.
  • Relevance scoring (BM25) uses term frequency, document frequency, document length, and field boosting (title > description > content, configurable).
  • Search engines also give typo tolerance and type-ahead experiences.
  • Options: PostgreSQL full-text search, or Elasticsearch, especially if your company already runs it (e.g., as part of the ELK stack for logs).
  • In the demo, Elasticsearch returned the same ~8,000 results in about 0.5 s vs about 7.5 s for Postgres ILIKE.
  • Field types: text (analyzed, full-text) vs keyword (exact match).
  • Master databases first; treat Elasticsearch as a tool you can pick up from the docs.

9. Possible Interview Questions to Prepare For

  1. Why does LIKE '%term%' become slow at scale? Why can't a normal index help?
  2. What is an inverted index? How does it differ from scanning documents?
  3. How does a search engine rank results? Explain term frequency, document frequency, document length, and field boosting.
  4. What is BM25?
  5. What is Apache Lucene and how does it relate to Elasticsearch?
  6. How would you support typo tolerance and type-ahead search?
  7. PostgreSQL full-text search vs Elasticsearch: how would you choose?
  8. What is the ELK stack, and what is Elasticsearch used for there?
  9. What is the difference between text and keyword fields in Elasticsearch?
  10. How would you keep an Elasticsearch index in sync with your primary database?
  11. How would you benchmark a database search against Elasticsearch fairly?
