Databases & PostgreSQL — Interview Notes

1. Why Databases? Persistence

Interacting with databases is one of the most frequent things a backend engineer does. At its core, a database is a way to persist information.

Persistence = storing data so that it survives after the program that created it has stopped — across sessions, restarts, and time.

Example: a to-do app. You add and check off tasks, close the app, reopen it later, and everything is still in the state you left it. Without persistence, every launch would start from scratch.

What counts as a "database"?

  • In the broadest sense, any structured storage offering create / read / update / delete (CRUD): a phone's contact list, the browser's localStorage / session storage / cookies (key–value stores), even a text file of notes.
  • In a backend context, "database" means a disk-based database (HDD/SSD) such as PostgreSQL, MySQL or MongoDB.

Why disk and not RAM?

%%{init: {'theme':'dark'}}%%
flowchart LR

For databases, capacity matters most and a speed trade-off is acceptable, so they live on disk. For a backend engineer, this is the level of detail that matters; storage engine internals are a much deeper topic.

2. DBMS — Database Management System

Just dumping data on disk isn't enough. You also need efficient ways to create, read, update, and delete it across hundreds or thousands of GBs. That is the job of a DBMS (e.g., PostgreSQL, MySQL, MongoDB).

%%{init: {'theme':'dark'}}%%
flowchart TD
    DBMS["DBMS"] --> A["Data organization
store data efficiently"]
    DBMS --> B["Access
efficient CRUD operations"]
    DBMS --> C["Integrity
data is accurate, valid, consistent"]
    DBMS --> D["Security
protect from unauthorized access: users and roles"]
  • Integrity example: an e-commerce payment column is numeric. The DBMS rejects an attempt to insert a string like "something" into it.

Why not just use text files?

  1. Parsing — to find a record you must write application code to read the file, split lines, and compare fields. This is slow (especially in slower languages like JavaScript, Python, Ruby) and error-prone; a bug can corrupt data.
  2. No structure — a text file accepts anything, so you can't enforce "this field is always a number". No consistency guarantees.
  3. Concurrency — two users updating the same value at the same time causes lost updates.
%%{init: {'theme':'dark'}}%%
sequenceDiagram
    participant A as User A adds 20
    participant B as User B subtracts 20
    participant F as Text file, amount is 40
    A->>F: read 40
    B->>F: read 40
    A->>F: write 60
    B->>F: write 20
    Note over F: Last write wins. Final value is 20 and A's update is lost

Depending on timing, the file could end up as 60 or 20 — there's no consistency. A DBMS has concurrency mechanisms to manage this correctly.

3. Relational vs Non-Relational Databases

Relational (SQL)Non-relational (NoSQL)
ExamplesPostgreSQL, MySQL, SQL ServerMongoDB
OrganizationTables, rows, columns; relationships via foreign keysCollections of documents
SchemaPredefined and strict — every column and type decided up frontFlexible — documents in the same collection can have different structures
Query languageSQL (Structured Query Language)Database-specific
StrengthStrong data integrity; complex queries and relationshipsFast prototyping; storing unpredictable content
WeaknessSchema changes require migrationsIntegrity is not enforced by the database — it moves into application code, which is more complex and error-prone

Terminology mapping: table ↔ collection, row ↔ document.

  • Good fit for relational: CRM (customer relationship management) — needs accurate, consistent data about contacts and sales opportunities, plus complex queries across relationships.
  • Good fit for non-relational: CMS (content management system) — articles can contain images, code blocks, embeds, and other unpredictable content types.

4. Why PostgreSQL?

  1. Open source and free — companies can self-host it.
  2. Sticks to the SQL standard — standard SQL runs the same on other systems, so migrating to MySQL or SQL Server later needs only minor changes.
  3. Extensible — a huge feature set (documentation is ~1,400 pages) and an extension system.
  4. Reliable and scalable.
  5. Excellent JSON support — native JSON / JSONB types with good indexing and query capabilities, so you rarely need a NoSQL database just for dynamic data.
Until you serve millions of users and need to optimize a specific bottleneck, the MySQL vs PostgreSQL performance debate doesn't matter. PostgreSQL is a strong default for most projects.

Note: SQL is the language; PostgreSQL is the database system that executes it. Basic SQL and Postgres (CREATE TABLE, SELECT, ORDER BY, GROUP BY, ...) are prerequisites; this chapter covers only what's most relevant to backend work. The demo uses TablePlus as the GUI client.

5. PostgreSQL Data Types

Numbers

TypeNotes
SERIAL / BIGSERIALAuto-incrementing integer (1, 2, 3, ...). BIGSERIAL has a much larger max; prefer it for production primary keys.
SMALLINT < INTEGER < BIGINTIntegers of increasing capacity — choose by the range you need.
DECIMAL(p, s) / NUMERIC(p, s)Exact numbers (treated identically). NUMERIC(10, 2) = at most 10 digits in total, exactly 2 after the decimal point (e.g., 12345678.90).
REAL, DOUBLE PRECISION, FLOATFloating-point: faster to store and compute, but not exact.
Rule of thumb: if accuracy matters (e.g., price, money) use DECIMAL/NUMERIC. If tiny discrepancies are harmless (e.g., an area or a scientific measurement) and speed matters, floating-point is fine.

Strings

TypeBehavior
CHAR(n)Fixed length; shorter values are padded with spaces to n.
VARCHAR(n)Variable length up to a maximum of n; longer values cause a database error.
TEXTVariable length with no declared limit (a very large upper bound).
  • CHAR: only when every value is guaranteed to be the same length (e.g., two-letter day codes such as Mo, Tu). Otherwise avoid it.
  • TEXT vs VARCHAR(n): the Postgres docs recommend TEXT, and there is no meaningful performance difference in Postgres. Many "VARCHAR(255)" habits come from MySQL and mean nothing in Postgres.
  • Why TEXT is preferred: changing a limit later needs a risky migration. An arbitrary number like 255 also misleads new team members into thinking it has meaning. Enforce length limits in application code instead.

Other types

  • BOOLEAN — true/false.
  • DATE, TIME, TIMESTAMP, TIMESTAMPTZ (TIMESTAMP WITH TIME ZONE — stores the time zone information too), INTERVAL (e.g., "10 days", "1 week").
  • UUID — a popular primary key choice (unique, non-guessable); Postgres has a native type.
  • JSON vs JSONB — JSON is stored as plain text. JSONB is stored in a Postgres-specific binary format for faster processing and querying. It is Postgres-specific (not part of the SQL standard); use JSONB in most cases.
  • Arrays of any type (e.g., INTEGER[]).
  • Special types: network addresses, MAC addresses, geometric points, XML — rarely needed day to day.

6. Migrations

In production you don't just open a GUI and run ad-hoc SQL. There'd be no record of what changed, who changed it, or when, and no way to control the database's version.

Database migrations = versioned SQL files, kept in your repo (e.g., db/migrations/) and applied in order by a command-line tool (dbmate, golang-migrate, etc.). 
%%{init: {'theme':'dark'}}%%
flowchart LR
    F["db/migrations/
001_create_users.sql
002_seed_data.sql
003_indexes_triggers.sql"] --> T["Migration tool (dbmate)
reads DATABASE_URL from .env
runs files in sequence"]
    T --> DB[("PostgreSQL")]
    T <--> S["schema_migrations table
stores the current version"]
  • File naming: sequential numbers or timestamps so the order is unambiguous (timestamps are common).
  • Up migration — the change to apply (create tables, types, indexes, ...).
  • Down migration — the exact reverse, used to roll back if something breaks. (Some modern workflows skip down migrations, but they are the standard approach.) In dbmate both live in the same file, separated by -- migrate:up and -- migrate:down comments.
  • The tool creates a table (schema_migrations) with a version column, recording what's already applied. On the next run it applies only the newer files; re-running old statements would fail with "table already exists".

Why migrations: (1) track database changes over time in version control; (2) roll back; (3) reproducible schema across environments. Relational databases have a strict schema, so every change (add a table, alter a column, create an index or trigger) goes through a new migration.

dbmate new create_users_table   # creates db/migrations/<timestamp>_create_users_table.sql
dbmate up                       # applies all pending migrations
dbmate down                     # rolls back the latest migration

Seeding

Seeding = inserting test data so you can exercise your queries and APIs in development. Best practice: put it in a separate migration file (e.g., dbmate new seed_data) that sorts after the schema migration. The seed uses CTEs (common table expressions) — e.g., insert users, RETURNING id, email, then insert profiles from that intermediate result.

Constraints — the tools of data integrity

ConstraintWhat it enforces
PRIMARY KEYUniquely identifies a row. Implicitly NOT NULL + UNIQUE, and automatically indexed.
NOT NULLThe column can't be empty. Columns allow NULL by default, so state it explicitly; the majority of your columns should be NOT NULL (buggy scripts can otherwise fill tables with NULLs).
UNIQUENo two rows can share the value (e.g., users.email).
CHECK (...)A custom condition, e.g., priority BETWEEN 1 AND 5.
DEFAULT ...Value used if none is supplied (e.g., gen_random_uuid(), NOW(), 'active').
REFERENCES (foreign key)The value must exist in the referenced table's key. Prevents orphan rows and invalid IDs.

Enum types

CREATE TYPE project_status AS ENUM ('active', 'completed', 'archived');
CREATE TYPE task_status    AS ENUM ('pending', 'in_progress', 'completed', 'cancelled');
CREATE TYPE member_role    AS ENUM ('owner', 'admin', 'member');
  • Data integrity — inserting any value outside the set is a database-level error, not just an application-level check.
  • Documentation (arguably the bigger win) — anyone reading the migrations sees the allowed values immediately, instead of digging through application code to find them.
  • Usually paired with a DEFAULT that is one of the enum values.

Naming conventions

  • Table names are plural (users, projects) — the most common convention, though teams may choose singular.
  • Tables and columns are lowercase snake_case (full_name, password_hash).
  • Why not camelCase: Postgres folds unquoted identifiers to lowercase, so fullName becomes fullname. You'd need double quotes ("fullName") everywhere, which makes code ugly.
  • The primary key column is conventionally called id.

Migration: tables (up), reconstructed from the walkthrough

-- migrate:up
CREATE TABLE users (
  id            UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  email         TEXT NOT NULL UNIQUE,
  full_name     TEXT NOT NULL,
  password_hash TEXT NOT NULL,   -- never store the plain-text password
  created_at    TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  updated_at    TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

-- one-to-one with users: the FK is also the PK
CREATE TABLE user_profiles (
  user_id    UUID PRIMARY KEY REFERENCES users,
  avatar_url TEXT,               -- optional fields: no NOT NULL
  bio        TEXT,
  phone      TEXT,
  created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

CREATE TABLE projects (
  id          UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  name        TEXT NOT NULL,
  description TEXT,
  status      project_status NOT NULL DEFAULT 'active',
  owner_id    UUID NOT NULL REFERENCES users ON DELETE RESTRICT,
  created_at  TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  updated_at  TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

CREATE TABLE tasks (
  id          UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  project_id  UUID NOT NULL REFERENCES projects ON DELETE CASCADE,
  title       TEXT NOT NULL,
  description TEXT,
  priority    INTEGER NOT NULL DEFAULT 1 CHECK (priority BETWEEN 1 AND 5),
  status      task_status NOT NULL DEFAULT 'pending',
  due_date    DATE,
  assigned_to UUID REFERENCES users ON DELETE SET NULL,
  created_at  TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  updated_at  TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

-- linking table for many-to-many between projects and users
CREATE TABLE project_members (
  project_id UUID NOT NULL REFERENCES projects ON DELETE CASCADE,
  user_id    UUID NOT NULL REFERENCES users ON DELETE CASCADE,
  role       member_role NOT NULL DEFAULT 'member',
  created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  PRIMARY KEY (project_id, user_id)   -- composite primary key
);

Relationship types and how to implement each

RelationshipExampleImplementation
One-to-oneusers ↔ user_profilesThe second table's primary key is also a foreign key to the first table (user_id UUID PRIMARY KEY REFERENCES users). No separate id.
One-to-manyone project → many tasksThe "many" side has a foreign key column (tasks.project_id) that is not its primary key.
Many-to-manyusers ↔ projectsA linking (junction) table with foreign keys to both, and a composite primary key of the two (PRIMARY KEY (project_id, user_id)). Data specific to the relationship (e.g., role) lives here.

Why a separate user_profiles table? Profile data (bio, phone, social links, website, ...) keeps growing. Keeping it in its own table means you don't keep altering the core users table. The same pattern is used for preferences and metadata.

Referential integrity: ON DELETE behavior

The foreign key's ON DELETE clause defines what happens to child rows when the referenced (parent) row is deleted.

8. From API to SQL

The flow for a request like GET /v1/users/:userId:

%%{init: {'theme':'dark'}}%%
flowchart LR
    FE["Front end"] -- "GET /v1/users/:userId" --> H["Handler"]
    H --> S["Service"]
    S --> R["Repository"]
    R -- "parameterized SQL" --> DB[("PostgreSQL")]
    DB -- "rows" --> R
    R -. "result, serialized to JSON in the response" .-> FE

Parameterized queries (prevent SQL injection)

A parameterized query puts an empty slot in the SQL and supplies the value separately. Whatever is passed is treated purely as data (escaped), never as SQL. This is the defense against SQL injection, which is what happens when you build queries by concatenating strings.

%%{init: {'theme':'dark'}}%%
sequenceDiagram
    participant App as Application (driver or ORM)
    participant DB as PostgreSQL
    App->>DB: Query text with a slot, WHERE id = $1
    App->>DB: Value sent separately, treated as data only
    Note over DB: Even a value like delete from users is just a string
    DB-->>App: Matching rows

In TablePlus the demo uses named slots (:user_id); real Postgres drivers typically use positional placeholders ($1, $2, ...). In application code, your driver or ORM handles the binding.

GET all users, with each user's profile embedded

SELECT u.*, to_jsonb(up.*) AS profile
FROM users u
LEFT JOIN user_profiles up ON u.id = up.user_id
ORDER BY u.created_at DESC;
  • Write FROM first (mentally) so you know where the data comes from; use short aliases (u, up).
  • LEFT JOIN vs INNER JOIN: some users may have no profile row. INNER JOIN would drop those users; LEFT JOIN keeps every user and returns a NULL profile. These are the two joins you'll use most.
  • to_jsonb(up.*) converts the profile row into a JSON object, embedded as the profile field, so one API call returns the user and profile together.
  • Always ORDER BY list queries. Without it, row order isn't guaranteed. The default is created_at DESC (latest first).

GET a single user

SELECT u.*, to_jsonb(up.*) AS profile
FROM users u
LEFT JOIN user_profiles up ON u.id = up.user_id
WHERE u.id = :user_id;

Dynamic filtering, sorting and pagination

List APIs must support optional filters, sorting, and pagination (as in the API design chapter). In a real backend you build the query dynamically: only add a WHERE condition if the client sent that parameter, and apply defaults for the rest.

%%{init: {'theme':'dark'}}%%
flowchart TD
    P["Query params: page, limit, letter, sortBy, sortOrder"] --> D["Apply defaults
page=1, limit=10, sortBy=created_at, sortOrder=desc"]
    D --> W{"letter passed?"}
    W -- Yes --> W1["Add name-prefix filter (ILIKE)"]
    W -- No --> O
    W1 --> O["Add ORDER BY using an allow-list of sortable fields"]
    O --> PG["Add LIMIT and OFFSET from page and limit"]
    PG --> E["Execute with bound parameters"]

SELECT u.*, to_jsonb(up.*) AS profile
FROM users u
LEFT JOIN user_profiles up ON u.id = up.user_id
WHERE u.full_name ILIKE :letter || '%'   -- names starting with the letter (case-insensitive)
ORDER BY u.email ASC                     -- sort field and direction chosen by the app
LIMIT :limit OFFSET :offset;             -- offset = (page - 1) * limit
  • ILIKE is a case-insensitive LIKE; 'J' || '%' matches names starting with J.
  • Pagination: the API's page starts at 1, but the SQL OFFSET starts at 0 — convert with (page - 1) * limit.
  • Important: values (letter, limit, offset, IDs) can be bound as parameters. Column names and ASC/DESC cannot in real drivers, so map the client's sortBy to an allow-list (e.g., full_name, email, created_at) and build that part in application code. Never insert raw client text there.

POST — create a user

INSERT INTO users (email, full_name, password_hash)
VALUES (:email, :full_name, :password_hash)
RETURNING *;

RETURNING * gives back the created row (with the generated id and timestamps), which becomes the API's 201 response body.

PATCH — partial update of a profile

Build the SET clause dynamically from only the fields the client sent (from an allowed set); untouched fields are left alone.

UPDATE user_profiles
SET bio = :bio, phone = :phone      -- only fields present in the payload
WHERE user_id = :user_id
RETURNING *;

9. Triggers — Auto-updating updated_at

Every update should refresh the row's updated_at. You could set it manually in every UPDATE from application code, or let the database do it with a trigger: an action that runs automatically when a condition (such as an update on a table) occurs.

%%{init: {'theme':'dark'}}%%
flowchart LR
    U["UPDATE on a row"] --> T["BEFORE UPDATE trigger fires"]
    T --> F["set_updated_at() sets updated_at to NOW()"]
    F --> W["Row is written with the fresh updated_at"]

CREATE OR REPLACE FUNCTION set_updated_at()
RETURNS TRIGGER AS $$
BEGIN
  NEW.updated_at = NOW();
  RETURN NEW;
END;
$$ LANGUAGE plpgsql;

-- one trigger per table (users, user_profiles, projects, tasks, ...)
CREATE TRIGGER trg_users_updated_at
BEFORE UPDATE ON users
FOR EACH ROW EXECUTE FUNCTION set_updated_at();
  • Name triggers clearly so the down migration can drop them (also drop the function and the indexes).
  • Demo result: after running the update query again, updated_at showed the current timestamp automatically.

10. Indexes

An index is like the index of a book: a lookup structure that lets the database jump straight to the data instead of scanning everything.

%%{init: {'theme':'dark'}}%%
flowchart TD
    Q["Query: WHERE id = X"] --> C{"Index on this column?"}
    C -- No --> S["Sequential scan
check every row, stored in different places on disk"]
    C -- Yes --> I["Look up X in the index
stored compactly in one place"]
    I --> L["Read the row's disk location"]
    L --> J["Jump straight to that row"]
    S --> R["Return the row"]
    J --> R
  • Without an index: a sequential scan — the database checks rows one by one across the disk. Fine for 6 rows, painful for millions or billions.
  • With an index: a lookup table of (column value → row location), kept in order and stored compactly. (Internals like B-trees are a separate topic.)
  • Order matters: an index can be ascending or descending. An index on created_at DESC serves a "latest first" query without re-sorting.
  • Primary keys are indexed automatically (and so are UNIQUE columns), but foreign key columns are not.

When to create an index

Consider indexing a column used in a join condition, a WHERE clause, or an ORDER BY — especially if the query runs frequently.

Trade-off

Indexes must be kept up to date. Every INSERT and UPDATE also updates the index, which adds write overhead. Weigh how often the query runs and the user experience you need. Start with the obvious ones, monitor performance, and drop indexes for queries that turn out to be rare.

Indexes used in the demo

-- migrate:up
CREATE INDEX idx_users_email              ON users (email);
CREATE INDEX idx_users_created_at         ON users (created_at DESC);          -- "get all users", latest first
CREATE INDEX idx_tasks_project_id         ON tasks (project_id);               -- FK used to join/fetch a project's tasks
CREATE INDEX idx_tasks_assigned_to        ON tasks (assigned_to);              -- FK used to fetch a user's tasks
CREATE INDEX idx_tasks_created_at         ON tasks (created_at DESC);          -- default sort of the tasks list
CREATE INDEX idx_tasks_status             ON tasks (status);                   -- filter tasks by status
CREATE INDEX idx_project_members_project  ON project_members (project_id);
CREATE INDEX idx_project_members_user     ON project_members (user_id);

Side note: users.email is already declared UNIQUE, and Postgres automatically creates an index to enforce uniqueness, so a separate index on it would be redundant. Check for that before adding one.

The same migration file also contains the set_updated_at() function and one trigger per table. The down section drops the triggers, the function, and the indexes.

11. Key Interview Takeaways

  • Persistence = data outlives the process. Backend "databases" are disk-based (large capacity, cheap, slower); caches like Redis live in RAM (fast, small, costly).
  • A DBMS provides organization, efficient CRUD access, integrity, and security. Plain text files fail on parsing cost, structure, and concurrency (lost updates).
  • Relational = tables, strict predefined schema, SQL, strong integrity (CRM-style data). Non-relational = flexible documents, integrity pushed to application code (CMS-style content).
  • PostgreSQL is a strong default: open source, SQL-standard, extensible, reliable, with excellent JSONB support.
  • Data types: BIGSERIAL/UUID for IDs; DECIMAL/NUMERIC for money and floats for tolerant, fast calculations; prefer TEXT over VARCHAR(255); use TIMESTAMPTZ, and JSONB over JSON.
  • Migrations = ordered, versioned SQL files (up and down) applied by a tool that tracks the current version. Seed test data in a separate migration.
  • Constraints (PRIMARY KEY, NOT NULL, UNIQUE, CHECK, DEFAULT, foreign keys) and enums protect integrity at the database level, and enums also document allowed values.
  • Relationships: one-to-one (PK is also FK), one-to-many (FK on the "many" side), many-to-many (linking table with a composite PK).
  • Referential integrity: ON DELETE RESTRICT / CASCADE / SET NULL / SET DEFAULT.
  • Use LEFT JOIN when the related row may not exist; INNER JOIN when both must match. Always ORDER BY list queries and paginate them.
  • Parameterized queries defend against SQL injection. Bind values as parameters; allow-list anything structural such as sort columns.
  • Triggers can automate work like refreshing updated_at.
  • Indexes speed up joins, filters, and sorts by avoiding sequential scans, at the cost of write overhead. Primary keys are indexed automatically; foreign keys are not.
  • Naming: plural, lowercase snake_case tables and columns (Postgres folds unquoted identifiers to lowercase).
