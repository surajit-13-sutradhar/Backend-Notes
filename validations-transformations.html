Validations & Transformations — Interview Notes

This chapter is less about a single concept and more about a set of rules/guidelines to follow when designing APIs — centered on data integrity and security.

1. Where This Fits in a Typical Backend Architecture

A typical backend has layered execution:

LayerResponsibility
Repository Layer (bottom)Database connections, query execution (inserts/deletes/updates), works with relational DBs, Redis, or any persistent storage
Service Layer (middle)Executes business logic — may call one or more repository methods, send notifications/emails, make webhook calls, etc.
Controller Layer (top)Calls the appropriate service method for a given API; handles all HTTP-related concerns (status codes, response format, and — the focus of this chapter — validations)

Why separate controller from service? We want to keep HTTP-related concerns (status codes, request/response formats, validation) isolated from the actual business logic, so the service layer stays clean and reusable regardless of transport (HTTP, gRPC, etc).

Key point: Validation and transformation happen at the entry point — after route matching, but before any significant controller logic runs (before calling service methods or executing business logic).

2. Why Validate at the Entry Point?

The idea: whatever data a client sends — JSON payload, query parameters, path parameters, headers — must be checked to ensure it's in the exact format the API expects before anything meaningful happens with it.

Example requirement: an API expects a JSON body with a field name that must be a string between 5–100 characters.

The validation pipeline (a reusable middleware/utility function backed by a schema) checks, step by step:

  1. Does the field name exist? If not → error: "name field is required."
  2. Is it the correct type (string)? If not → error: "expected string, received boolean" (or whatever type was sent).
  3. Does it satisfy length constraints (5–100 chars)? If not → error about length.

What happens without validation? (Failure scenario)

Imagine no validation pipeline exists, and a client sends {"name": 0}" (a number, not a string) for an API that creates a "book" row.

  • Data flows unchecked: Controller → Service → Repository → Database.
  • The database column name is defined as TEXT NOT NULL (e.g., in Postgres).
  • Postgres enforces its own type constraints and the insert **fails** because a number was provided where text was expected.
  • Depending on error handling, the client gets a generic 500 Internal Server Error — a poor user experience, since it gives no indication of what actually went wrong.

With validation at the entry point: the same bad input is caught immediately and the client receives a clear 400 Bad Request with an explanation of exactly what's wrong — before the request ever touches the service or repository layers.

3. Demo Recap (Syntactic Example)

API: POST /api/valid/syntactic

  • Sending an empty JSON payload → error array listing three required fields: email, phone, date.
  • Providing dummy values → errors: invalid email format, and phone expected string but received number.
  • Fixing the email (e.g. test@test.com) and quoting the phone as a string → request succeeds with 200 OK.

4. Three Types of Validation

TypeChecks whether…Examples
Syntactic The data follows the correct structure/pattern Email format (local@domain.tld), phone number structure (country code + digits), date format (e.g. YYYY-MM-DD)
Semantic The data makes logical sense Date of birth cannot be in the future; age of 365 doesn't make sense; age must realistically be between 1–120
Type The data is of the correct data type Is this field a string, number, boolean, array, or nested object as expected?

4.1 Syntactic Validation — Example

Validating an email, phone number, or date against their expected structural pattern (e.g., name@domain.tld for email).

4.2 Semantic Validation — Example

API expects dateOfBirth and age:

  • Setting dateOfBirth to a future year (e.g. 2026 when "today" is 2025) → error: "date of birth cannot be in the future."
  • Setting age to 430 → error: "number must be less than or equal to 120."

Semantic validation checks that data is not just correctly typed/structured, but logically valid.

4.3 Complex / Cross-Field Validation — Example

API expects password, passwordConfirmation, and married:

  • password must be at least 8 characters.
  • passwordConfirmation must exactly match password — otherwise error: "passwords don't match."
  • If married is true, an additional field partner (the partner's name) becomes required. If married is false, partner is optional.

This shows validation pipelines can express conditional/cross-field business rules, not just single-field checks.

4.4 Type Validation — Example

API expects: stringField, numberField, arrayField, boolField.

  • Sending a string where a number is expected → "expected number, received string."
  • Sending a string where an array is expected → "expected array, received string."
  • Array elements can have their own type constraints — e.g., an array of numbers sent where an array of strings was required → error pinpointing the exact index: "element 0: expected string, received number."

5. Transformation

Transformation = converting/casting data into a desired format, either before validation (so it *can* be validated correctly) or after, to prepare it for the service layer.

Example: Query Parameter Casting

Endpoint: /bookmarks?page=2&limit=20

  • Requirement: page must be a number, greater than 0 and less than 500. limit must be a number, greater than 0 and less than 10,000.
  • Problem: query parameters always arrive as strings by default — regardless of what they "look like." So page=2 arrives as the string "2", not the number 2.
  • If validation runs directly on this raw string against a "must be a number" rule, it would fail incorrectly — even though the client did nothing wrong. This is the server's responsibility to fix.
  • Solution: the server/service must cast (transform) the string into a number before running the numeric validation rules.
Cast = forcing one data type to convert into another (e.g., string "20" → number 20).

Validation and transformation are usually paired into a single pipeline so all input-handling logic (format expectations + data massaging) lives in one place, rather than scattered across the codebase.

Example: Server-Side Normalization

Sending an email with mixed casing (e.g. Test@Example.COM), a phone number without a leading +, and a date in one format:

  • The server transforms the email to all lowercase before using it.
  • The server prepends a + to the phone number.
  • The date gets reformatted into the server's expected structure.

This is transformation happening as part of the same pipeline — normalizing client input into a canonical format the service layer expects, regardless of exactly how the client sent it.

6. Frontend Validation vs Backend Validation

A common mistake: assuming frontend (client-side) validation can replace backend (server-side) validation.

Frontend ValidationBackend Validation
PurposeUser Experience (UX) — immediate feedbackSecurity & Data Integrity — mandatory
Can it be bypassed?Yes — easily, e.g. via API clients like Postman/Insomnia that skip the UI entirelyNo — it's the last line of defense before data touches business logic/DB
Is it required?Nice to have, improves UXAlways required, regardless of what client is used
Any server can be hit by multiple kinds of clients — a polished web app with rich frontend validation, or a raw API client like Postman/Insomnia with no frontend validation at all. If backend security/integrity depends on frontend validation having run, the system breaks the moment a different (or malicious) client is used.

Rule of thumb: Design server-side validation to be as strict and specific as necessary, completely independent of whatever the frontend does or doesn't do. Frontend and backend validation work together — frontend for UX, backend for correctness and security — but backend validation must never be skipped or treated as optional.

7. Key Interview Takeaways

  • Validation and transformation happen at the entry point — after route matching, before any business logic in the controller/service/repository layers runs.
  • Why validate early: prevents unexpected/invalid data from propagating deep into the system (e.g., causing a raw DB-level type error and an unhelpful 500), and instead returns a clear, actionable 400 Bad Request.
  • Three types of validation:
    • Syntactic — correct structure/pattern (email, phone, date formats).
    • Semantic — data makes logical sense (DOB not in future, realistic age range).
    • Type — correct data type (string/number/boolean/array/object).
  • Validation pipelines can also express cross-field / conditional rules (e.g., password confirmation must match; a field becomes required only if another field has a specific value).
  • Transformation = casting/normalizing data into the format the service layer expects (e.g., query params are always strings and must be cast to numbers/booleans before numeric/boolean validation can run correctly).
  • Validation and transformation are typically combined into a single pipeline, keeping all input-handling rules centralized rather than scattered.
  • Frontend validation ≠ backend validation. Frontend validation is for UX (immediate feedback); backend validation is mandatory for security and data integrity, since frontend checks can always be bypassed (e.g., via direct API calls with tools like Postman/Insomnia).

8. Possible Interview Questions to Prepare For

  1. Where in the request lifecycle should input validation happen, and why?
  2. What's the difference between syntactic, semantic, and type validation? Give an example of each.
  3. Why are query parameters always strings, and what problem does that create for validation? How do you solve it?
  4. What's the difference between validation and transformation?
  5. Why is it a bad idea to rely solely on database-level constraints to catch invalid input?
  6. Why should frontend validation never replace backend validation?
  7. How would you design a validation rule where one field's requirement depends on another field's value (e.g., "partner" required only if "married" is true)?
  8. What status code should a validation failure return, and why (400 vs 500)?
