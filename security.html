Backend Security — Interview Notes

1. The Mindset

Security is a huge domain: browser security (HTML, cookies, local storage), network security (HTTP/HTTPS, encryption), server/OS security, and backend application security (the vulnerabilities that come from the code you write). This chapter covers only the last one, practically.

  • The goal is not to learn a bag of fancy techniques. No application can ever be truly secure. The goal is to become paranoid: keep security at the back of your head whenever you write code.
  • Think like an attacker. Attackers don't care about your framework or language. They ask one question: "Where did the developer make an assumption?"
  • Typical assumptions: the input is clean; the user is who they say they are; the request comes from my front end; nobody will open the network tab and modify parameters. Under deadlines, these assumptions feel reasonable because you're thinking about the happy path. Attackers poke every boundary and guess every assumption.
  • Every time you write code, ask: "What could go wrong here, security-wise?"

2. Injection Attacks

The root cause

Your application speaks multiple languages to different systems, and each has its own grammar and special characters:

%%{init: {'theme':'dark'}}%%
flowchart LR
    U["User
types input in the browser"] --> A["Your backend"]
    A -- "SQL" --> DB[("Database")]
    A -- "HTML, CSS, JavaScript" --> BR["Browser"]
    A -- "Shell commands" --> OS["Operating system"]
An injection happens when user input crosses the boundary into another language and is interpreted as code instead of treated as data. That confusion between code and data is the root cause of all injection attacks (SQL injection, command injection, XSS, ...).

SQL injection

A login handler builds its query by concatenating strings (vulnerable; shown for illustration):

query = "SELECT * FROM users WHERE email = '" + email + "'"
InputResulting queryEffect
alice@gmail.com (happy path)SELECT * FROM users WHERE email = 'alice@gmail.com'Returns Alice's row.
' OR '1'='1' --SELECT * FROM users WHERE email = '' OR '1'='1' --'The first ' closes the string, so the left side is email = '' (false). '1'='1' is always true, so the WHERE is always true. -- comments out the leftover quote. Every user is returned.
'; DROP TABLE users; --SELECT * FROM users WHERE email = ''; DROP TABLE users; --'A second statement runs and can delete the table.
  • The characters aren't malicious by themselves. They become malicious once combined with your SQL template, where ' delimits strings, ; separates statements, -- starts a comment, and words like OR / DROP are keywords. Concatenating means trusting that the input contains none of these, which is impossible even for benign users.
  • In the demo, the DROP TABLE variant did not run: many modern drivers block multiple statements in one query by default. Older drivers may allow it.
  • Attackers can do much more: UNION statements to extract data from other tables (e.g., payment info), database functions to read files from the server, and in some configurations execute OS commands.

Fix 1: parameterized queries (prepared statements)

Send the query structure and the data to the database separately. The value only ever fills a slot and is treated purely as data.

%%{init: {'theme':'dark'}}%%
sequenceDiagram
    participant App as Backend
    participant DB as Database
    App->>DB: 1. Query template with a slot, WHERE email = $1
    App->>DB: 2. The value, sent separately as data
    Note over DB: A value like ' OR '1'='1 is just a garbage string, not an email, so no rows match
    DB-->>App: Result

db.query("SELECT * FROM users WHERE email = $1", [userInput]);
  • Every modern database driver supports this and every ORM uses it by default. You are only vulnerable if you deliberately bypass it by building raw strings.
  • Your validation layer should also reject something that doesn't look like an email before it ever reaches the query. Parameterization is the safety net if validation is weak.

Fix 2: least-privilege database user

The credentials your app uses to connect should only have permission for DML (data manipulation: INSERT, UPDATE, DELETE, SELECT), not DDL (data definition: DROP, ALTER, ...). Run migrations with a separate, more privileged user. Even if an injection slips through, it can't drop tables.

NoSQL injection

Using MongoDB doesn't make you safe. Queries are JSON objects that can contain operators ($ne, $gt, $exists, ...). If you pass user-supplied JSON straight into a query, an attacker can control the structure, not just the value. For example, sending {"$ne": null} where a string email was expected.

Command injection

Same idea, but the target is the operating system. Example: an image-upload service shells out to a CLI tool such as FFmpeg, and the output file name comes from the user:

ffmpeg -i input.png -vf scale=220:120 -o <userSuppliedName>

# user supplies:  out.jpg; rm -rf /
# the shell sees two commands, and the second one deletes the filesystem
  • Attackers can also use pipes (|) to redirect output to other commands or & to run things in the background (e.g., spyware). Every shell has its own special characters.
  • Fix: use your language's process-execution API that takes the command and its arguments as separate parameters (an argument array). The arguments go directly to the process and never through a shell interpreter, so they are treated as plain strings.

The mental model

Target systemUnsafeSafe
SQL databaseString concatenation or templatesParameterized queries
Operating systemBuilding a shell command stringArgument arrays, no shell
Any interpreter (NoSQL, HTML, LDAP, XML, ...)Mixing user input with control syntaxAPIs that separate structure from data

Whenever you build a string that another system will interpret and it contains user input, stop and look for a parameterized alternative. One almost always exists.

3. Authentication

Authentication = verifying the user's identity (which row in users this person is). Get it wrong and attackers can impersonate users, read their data, act on their behalf, and steal money (account takeover).

Advice: use an auth provider if you can

  • Production auth is far more than "verify a JWT and store it in a cookie": stateful sessions (track devices, revoke one or all sessions), social login (Google, GitHub) with OAuth flows in both back end and front end, linking email/password and social accounts for the same email, RBAC, timeouts, cache and database revocation, and more.
  • Providers (e.g., Clerk, Auth0) save weeks of time and salary, and have dedicated security teams responding to new attacks 24/7. The bill only becomes large when you have thousands or millions of users, by which point you probably have revenue and can consider building your own.
  • Even with a provider, you must understand how auth works to configure and integrate it securely.

Password storage

%%{init: {'theme':'dark'}}%%
flowchart TD
    A["1. Plain text
a breach leaks every password, and insiders can read them
users reuse passwords across sites"] --> B["2. Hash the password
one-way, fixed length, deterministic"]
    B --> C["Problem: rainbow tables
precomputed hashes of common passwords"]
    C --> D["3. Add a random salt per user
identical passwords give different hashes"]
    D --> E["Problem: brute force on fast hashes
GPUs compute billions of SHA-256 hashes per second"]
    E --> F["4. Use a slow password hash with a cost factor
bcrypt, scrypt, Argon2id"]
  1. Plain text is wrong. Databases get breached daily, at companies of every size, and by insiders or third parties. Most users reuse passwords, so a leak compromises their accounts elsewhere (banking, e-commerce, social media). Even without a breach, any developer or DBA with database access can read everyone's passwords.
  2. Hashing. A hash function accepts input of any length and always returns a fixed-length output; the same input always gives the same output; and it is one-way (you can't recover the input from the output). Store the hash. At login, hash the attempt and compare with the stored hash.
  3. Rainbow tables. Because hashes are deterministic, attackers keep huge tables mapping common passwords (123456, password) to their hashes, and look up a leaked database against them.
  4. Salting. Generate a random per-user string (from a cryptographically secure random generator), combine it with the password, then hash. Now identical passwords produce different hashes, so precomputed tables no longer match.
  5. Brute force. An attacker with your leaked database can still take each user's salt and guess passwords offline. Modern GPUs compute billions of general-purpose hashes (SHA-256, MD5) per second, so every password up to 8 characters or common pattern falls in days.
  6. Slow hashes. Use algorithms designed for passwords: bcrypt, scrypt, and now the industry standard Argon2id. They have a tunable cost (work) factor. If a hash takes ~400 ms, that's imperceptible for a real user logging in, but it cuts an attacker from billions of guesses per second to a handful, turning days into decades or centuries. Do not use MD5 or SHA-256 for passwords.

Note: libraries like bcrypt and Argon2 generate the salt for you and embed it in the output hash string, so you usually don't need a separate salt column. Good reading: Lucia's auth guides (a resource on implementing auth with best practices) and the OWASP cheat sheets.

Sessions (stateful authentication)

After login, you can't ask for the password on every request. On successful login the server:

  1. Generates a random session identifier from a cryptographically secure pseudo-random number generator, with at least 128 bits of entropy. If an attacker could guess it, they could hijack sessions.
  2. Stores it server-side (Redis for speed, or your primary database) along with metadata: which user, created time, expiry (e.g., 7 days), IP address and user agent (to show "where you're logged in" and support revocation).
  3. Sends it to the browser in a cookie. The browser returns it on every request.
%%{init: {'theme':'dark'}}%%
sequenceDiagram
    participant B as Browser
    participant S as Server
    participant R as Session store, Redis or DB
    B->>S: Email and password
    S->>S: Verify against the stored password hash
    S->>R: Create session, random ID with user, expiry, IP, user agent
    S-->>B: Set-Cookie with the session ID
    B->>S: Later request, cookie sent automatically
    S->>R: Look up the session ID
    R-->>S: Session, so we know the user
    S-->>B: Response

Cookie security flags

Set-Cookie: sid=<random>; HttpOnly; Secure; SameSite=Strict; Path=/; Max-Age=604800
FlagEffect
HttpOnlyJavaScript cannot read the cookie. If your site has an XSS vulnerability, injected scripts can't steal the session ID or token. (This is why storing tokens in localStorage is discouraged.)
SecureThe browser only sends the cookie over HTTPS. Over plain HTTP, traffic can be intercepted on public Wi-Fi, by a malicious ISP or router, or with tools like Wireshark.
SameSiteControls whether the cookie is sent on cross-site requests. Strict: only for requests that originate from your own site. Lax: also sent on top-level navigations (a link to your site) but not from images/iframes. None: sent on all requests and requires Secure. For session cookies use Strict (or Lax if front end and back end are on different domains); avoid None. This defends against CSRF.

Stateless authentication: JWT

With sessions, the server keeps the session data and gives the client just an ID. With a JWT (JSON Web Token), the session data itself is sent to the client, and the client sends it back on every request.

%%{init: {'theme':'dark'}}%%
flowchart LR
    H["Header
token type and signing algorithm"] --- P["Payload, the claims
sub: user ID, iat: issued at, custom claims such as name or admin"] --- S["Signature
signature of header and payload, made with a server-side secret"]
  • Why can't the client just claim to be someone else? The server signs header + payload with a secret. On each request it verifies the signature with the same secret. If anyone edits the payload (even changing "John Doe" to "John Do"), verification fails and the server rejects it.
  • The payload is only Base64-encoded, not encrypted. Anyone can decode and read it. Never store sensitive data in a JWT.
  • Advantage: the server stores nothing, so it scales easily with no database or Redis lookup.

JWT drawbacks

  1. Revocation is hard. With sessions you delete the row and the user is out immediately. With JWTs you can't recall a token the client holds. If an account is compromised, you can't force-logout all devices.
    • Workaround: a blacklist of revoked tokens (in Redis or the database).
    • Workaround: short-lived access tokens + refresh tokens (below).
  2. Storage. localStorage is readable by any script, so an XSS vulnerability leaks the token. An HttpOnly cookie avoids that, but then you're back to a cookie-based flow.
%%{init: {'theme':'dark'}}%%
sequenceDiagram
    participant C as Client
    participant S as Server
    C->>S: Login
    S-->>C: Access token, valid about 5 minutes, and refresh token, valid about 1 to 7 days
    C->>S: Request with the access token
    S-->>C: Response
    Note over C,S: Access token expires
    C->>S: Request with the expired access token
    S-->>C: 401 Unauthorized
    C->>S: Send the refresh token
    S->>S: Check that the refresh token is valid and not expired
    S-->>C: New access token and new refresh token
Advice: unless you have specific scaling needs, prefer stateful, session-based authentication. Even with multiple servers, sessions can live in a distributed store like Redis. Revocation is simple and the architecture fits most SaaS products. If you do use JWTs: use short expiry (minutes to hours, not days), refresh tokens with server-side storage, and HttpOnly cookies instead of localStorage.

Rate limiting authentication

Without rate limiting, an attacker can try thousands or millions of credential combinations per minute, or just flood the server until it crashes. Auth endpoints should be stricter than general endpoints, and use layers:

LayerExampleStopsWeakness
Per IP10 login attempts per minute per IPSimple automated attacksMany users can share one IP (universities, offices), and attackers rotate IPs (botnets, proxies, VPNs).
Per account5 failures in 15 minutes locks the account (e.g., 24 hours or until support)IP rotation against one accountDoesn't stop one password tried across many accounts.
GlobalAlert when the system-wide failed-login rate passes a threshold (e.g., 100 per minute)Distributed attacks across IPs and accountsNeeds a response: raise an alert, block IPs, show a CAPTCHA.

4. Authorization

Authentication answers "who is this?". Authorization answers "what are they allowed to do?". The dangerous confusion is in implementation.

%%{init: {'theme':'dark'}}%%
flowchart TD
    R["Routing layer
authentication middleware, role check, permission check such as read books"] --> H["Handler"]
    H --> S["Service"]
    S --> RP["Repository
SELECT * FROM books WHERE id = 5"]
    RP --> Q{"Does this query also check that the book belongs to this user?"}
    Q -- "No" --> BAD["Broken object level authorization
any user can read book 5"]
    Q -- "Yes: AND user_id = context user" --> OK["Only the owner's data is returned"]

Passing authentication and even a "read books" permission at the routing layer creates a false sense of security. It does not mean the user may access every book.

BOLA — Broken Object Level Authorization (a.k.a. IDOR, Insecure Direct Object Reference)

  • What: the system checks auth at the routing layer but doesn't check ownership at the data level. Example: GET /books?id=5, where book 5 isn't the user's.
  • Impact: a script can iterate through IDs and download every invoice or payment record, or modify them.
  • Fix: verify access at the point of access, in the query itself:
SELECT * FROM invoices WHERE id = :id AND user_id = :contextUserId;

This applies to every query: reads, updates, deletes, and inserts, not just SELECT.

Don't leak existence: 404, not 403

Some engineers fetch invoice 5, then compare the owner and return 403 Forbidden on a mismatch. That confirms invoice 5 exists, so an attacker can enumerate valid IDs and plan further attacks (like social engineering). Instead, use the single ownership query above. A missing row returns 404 Not Found, and the attacker can't tell "doesn't exist" from "exists but isn't yours".

BFLA — Broken Function Level Authorization

  • What: access to sensitive functions (not data) isn't restricted. Example: /admin/invoices returns all invoices and has no admin check, because "only admins know the URL".
  • That's security through obscurity: hiding instead of protecting. Anyone watching traffic, or any logged-in user who finds the URL, can call it.
  • Fix: add a role check in the routing layer (e.g., role = admin) in addition to the granular permission (e.g., read invoices, which both members and admins may have).

Predictable IDs

Sequential IDs (101, 102, 103) let attackers guess and enumerate resources. Random UUIDs make guessing impractical (with some performance considerations to read about). This is a mitigation, not a replacement for authorization checks.

A simple model: horizontal vs vertical

%%{init: {'theme':'dark'}}%%
flowchart LR
    subgraph HZ["Horizontal: same privilege level"]
        UA["User A"] -- "reads or changes" --> UB["User B's resources
BOLA / IDOR"]
    end
    subgraph VT["Vertical: higher privilege level"]
        M["Regular member"] -- "calls" --> AF["Admin-only functions

    end

Framework for preventing authorization bugs

  1. Centralize authorization logic in one clear layer, so it's consistent, understandable, and maintainable, not scattered and easy to forget.
  2. Default deny: anything not explicitly allowed is denied. New resources and endpoints are protected until you grant access.
  3. Test authorization explicitly and automatically. Beyond the happy path: user A can't access user B's data, a member can't call admin functions, and an unauthenticated user can't reach protected resources. Run the tests in CI/CD so future changes can't silently open a hole.
  4. Audit logs: record access to sensitive resources (e.g., admin endpoints) and flag failed authorization attempts as security events, since someone may be probing your system.

5. XSS — Cross-Site Scripting

XSS = an attacker gets their JavaScript to execute in another user's browser, in the context of your site. Root cause: user-provided content is treated as code rather than data.

Why it's dangerous: JavaScript on your page can read everything on it (including sensitive data), read cookies and local storage that aren't HttpOnly, make API calls as the logged-in user, redirect users to phishing pages, and alter the page to impersonate another site.

Stored XSS example

A blog platform has comments written in markdown, converted to HTML and injected into the DOM. If the attacker finds a way to get a <script> tag into that HTML and it's stored and rendered without sanitization, it runs for every user who views the comment.

%%{init: {'theme':'dark'}}%%
sequenceDiagram
    participant A as Attacker
    participant S as Server and database
    participant V as Victim's browser
    A->>S: Post a comment containing a script tag
    Note over S: No sanitization, so it is stored as is
    V->>S: Open the page with the comment
    S-->>V: HTML including the attacker's script
    Note over V: The script runs as if it were your site's code
    V->>A: Script sends cookies and tokens to the attacker's server
  • React deliberately names its raw-HTML prop dangerouslySetInnerHTML to warn you that you are on your own regarding XSS. Libraries like Remark/Rehype and frameworks have safety mechanisms built in, but if you inject HTML yourself, you're responsible.
  • Other kinds: reflected XSS (a script in the URL is echoed back in the page) and DOM-based XSS (client-side code writes untrusted data into the DOM, such as setting innerHTML).

Prevention

  1. Sanitize user-provided markup (strip script tags and other dangerous constructs, ideally with a well-tested sanitizer library rather than hand-rolled rules), and rely on your framework's default output escaping where possible.
  2. CSP (Content Security Policy) — an HTTP response header telling the browser what it may execute or load: only scripts from specific domains, no inline scripts, images only from certain domains, and so on. An injected script tag would be blocked by the browser. CSP is defense in depth, the last line of defense, not the primary fix. You still need to fix the root cause.
  3. Use HttpOnly cookies so injected scripts can't read session cookies.
Content-Security-Policy: default-src 'self'; script-src 'self'

General rule: every time you handle user-provided content (a search query, HTML, an image, a file), think about what it can do and what resources it can consume.

6. CSRF — Cross-Site Request Forgery

Covered briefly because it's much less of a threat on modern stacks, though legacy systems remain exposed. It works because browsers automatically attach cookies to requests to a site, even when the request is triggered from a different site.

%%{init: {'theme':'dark'}}%%
sequenceDiagram
    participant U as User, logged in to bank.com
    participant E as evil.com
    participant B as bank.com
    U->>E: Visits a malicious page, for example via a phishing link
    E-->>U: Page with an auto-submitting form or an image pointing at bank.com
    U->>B: Browser sends the request and automatically attaches the bank.com cookie
    Note over B: The server sees a valid session and performs the action

Why it's mostly handled today:

  • SameSite cookies (Strict or Lax) stop the cookie from being sent on such cross-site requests. Modern browsers default to Lax, so you're protected unless you set None.
  • CORS configuration is not a security mechanism as such, but it is an additional line of defense: your server only allows requests from your own front end origin.
  • Legacy or cookie-heavy systems can also use anti-CSRF tokens.

7. Misconfiguration

Secrets management

  • Secrets = API keys, database passwords, encryption keys, JWT/auth secrets.
  • Never put secrets in source code or commit them to Git. Anyone with repository access could use your database and external services.
  • Keep them in environment variables or a secret manager (AWS Parameter Store, HashiCorp Vault, etc.).
  • If a secret is ever committed, deleting it isn't enough, because it remains in the commit history. Rotate it (revoke and create a new one).

Debug mode in production

  • Locally you log at debug level: stack traces (which reveal function names, file names, code structure), SQL queries, database configuration, transaction details, and possibly user data.
  • In production, the log level should be info or higher. Otherwise a breach of your logs (or verbose errors returned to clients) hands attackers a map of your system and users' data.
  • Be deliberate about the log level in local, staging, and production.

Security headers

  • CSP (above) and X-Frame-Options (or CSP frame-ancestors), which stop other sites from embedding yours in an <iframe>. This prevents clickjacking: an attacker hosts your site invisibly in a frame and tricks users into clicking or entering data.
  • Other industry-standard headers exist. Web frameworks in every language provide a security-headers middleware (e.g., Helmet for Express) that sets them with a one-line change.

8. The Big Picture

Every vulnerability above is about boundaries: data crossing between systems, privilege levels, languages, or markup contexts.

  • SQL injection: untrusted input crosses into the database query language.
  • XSS: user markdown crosses into HTML/JavaScript.
  • Broken authorization: requests cross the boundary of what each user should access.

Every time you write code, ask three questions:

  1. Where is data crossing a boundary?
  2. What assumptions am I making about that data?
  3. What if those assumptions are wrong?

Defense in depth

No single defense is perfect, so think in layers. An attacker must bypass all of them.

%%{init: {'theme':'dark'}}%%
flowchart TD
    I["Incoming request"] --> L1["1. Input validation
strictly validate everything at the entry point"]
    L1 --> L2["2. Parameterized operations
SQL parameters, argument arrays, never string concatenation"]
    L2 --> L3["3. Authorization at the point of access
check ownership and role where the data is touched"]
    L3 --> L4["4. Headers and policies
CORS, CSP, security headers limit the damage if something slips through"]
    L4 --> L5["5. Monitoring and logging
log suspicious activity, raise alerts"]
Security is not a list of techniques to implement. It's a mindset: be paranoid about your systems before writing every line of code.

10. Key Interview Takeaways

  • Think like an attacker: "where did the developer make an assumption?" No application is truly secure; be paranoid.
  • Injection = user data interpreted as code (SQL, shell, NoSQL operators, HTML/JS). Fix: separate structure from data. Use parameterized queries and argument arrays, validate input, and use a least-privilege (DML-only) database user.
  • Passwords: never plain text. Use a slow, salted password hash (Argon2id, bcrypt, scrypt) with a cost factor. Not MD5 or SHA-256. Salt defeats rainbow tables; slowness defeats brute force.
  • Sessions: a random ID from a CSPRNG, stored server-side (Redis or DB), sent in a cookie with HttpOnly, Secure, SameSite.
  • JWT: header.payload.signature. The payload is readable (Base64) but tamper-proof (signed). Revocation is hard. Mitigate with short-lived access tokens + refresh tokens. Prefer sessions unless you have specific scaling needs.
  • Rate limit auth endpoints in layers: per IP, per account, and global.
  • Authorization must be checked at the point of access, not only at the routing layer. BOLA/IDOR (horizontal) and BFLA (vertical). Return 404 instead of 403 to avoid leaking existence. Use UUIDs, but never treat them as a substitute for checks.
  • Authorization framework: centralize, default deny, automated tests, audit logs.
  • XSS: attacker JavaScript runs in the victim's browser. Prevent with sanitization/escaping, HttpOnly cookies, and CSP as defense in depth. CSRF: largely mitigated by SameSite cookies (and CORS).
  • Misconfiguration: keep secrets out of Git (and rotate leaked ones), don't run debug logging in production, and set security headers (CSP, clickjacking protection).
  • Defense in depth: validation → parameterized operations → authorization at the point of access → headers and policies → monitoring and logging.

11. Possible Interview Questions to Prepare For

  1. What is SQL injection? Walk through how ' OR '1'='1' -- changes a query.
  2. How do parameterized queries prevent SQL injection? What else limits the damage (least-privilege DB user)?
  3. Is NoSQL immune to injection? What is command injection and how do you prevent it?
  4. Why is storing plain-text passwords wrong? How do hashing, salting, and slow hashing each help? Why not SHA-256?
  5. What is a rainbow table? What is a cost (work) factor?
  6. How do session-based and JWT-based authentication differ? Trade-offs?
  7. Why is JWT revocation hard, and what are the workarounds? What are access and refresh tokens?
  8. Where should you store a session token or JWT in the browser, and why?
  9. What do HttpOnly, Secure, and SameSite do?
  10. How would you rate limit a login endpoint? Why is one layer not enough?
  11. What are BOLA/IDOR and BFLA? Give examples and fixes.
  12. Why return 404 rather than 403 for resources the user doesn't own?
  13. Horizontal vs vertical privilege escalation?
  14. How would you design authorization so mistakes are unlikely (centralized, default deny, tests, audit logs)?
  15. What is XSS? Types? How do sanitization and CSP help, and why isn't CSP the primary fix?
  16. What is CSRF, and why does SameSite mostly solve it?
  17. How should secrets be managed? What if one is committed to Git?
  18. Why is debug logging in production a security risk?
  19. What is clickjacking and which header defends against it?
  20. What is defense in depth? Name the layers you would put in a backend.
