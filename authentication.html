Authentication & Authorization — Interview Notes

1. Core Definitions (2-sentence summary)

TermQuestion it answersMeaning
Authentication (AuthN)"Who are you?"Mechanism to assign/verify an identity to a subject, in a given context (platform, OS, device, etc.)
Authorization (AuthZ)"What can you do?"Determines the permissions/capabilities a subject has in that context
Authentication always happens before authorization — you must know who someone is before deciding what they can do.

2. Historical Evolution of Authentication (context, not usually asked directly but good to know)

%%{init: {'theme':'dark'}}%%
timeline
    title Evolution of Authentication
    Pre-Industrial : Implicit trust (village elder vouching, handshake deals)
    Medieval Period : Wax seals — "something you have" (first forgeries = first bypass attacks)
    Industrial Revolution : Telegraph passphrases — "something you know" (shared static secrets)
    1961 (MIT CTSS) : First digital passwords (stored in plaintext — leaked via printed file!)
    1970s : Diffie-Hellman asymmetric crypto, PKI, Kerberos (ticket-based auth)
    1990s : MFA (know + have + are), biometrics
    21st Century : OAuth, JWT, Zero Trust, WebAuthn (passwordless)
    Emerging/Future : Decentralized identity (blockchain), behavioral biometrics, post-quantum crypto

Key evolution of trust principles:

  1. Something you have (seal, smart card, OTP device)
  2. Something you know (password, PIN, passphrase)
  3. Something you are (biometrics)
  4. MFA = combining 2 or more of the above

Why plaintext passwords are bad: MIT CTSS (1961) incident — a password file was printed in plaintext and exposed → birth of secure password storage → hashing (irreversible, fixed-length output regardless of input length; same input always produces same output).

3. Three Foundational Building Blocks

Before diving into auth types, three recurring concepts:

A. Sessions

  • HTTP is stateless by design — every request is independent, server remembers nothing between requests.
  • This was fine for static content but broke down once the web needed stateful interactions (shopping carts, staying logged in).
  • Session mechanism:
    1. User logs in → server creates a unique session ID, stores it + user data (role, cart, etc.) in a persistent store (DB or Redis/Memcached — in-memory stores are faster).
    2. Session ID sent to client as a cookie.
    3. Every subsequent request auto-includes the cookie → server looks up session ID in the store → retrieves user context.
    4. Sessions are short-lived (expiry) — new session generated after expiry.
  • Evolution of session storage: file-based → database-backed → distributed in-memory stores (Redis, Memcached) for scalability.

B. JWT (JSON Web Token)

  • Emerged because stateful sessions don't scale well in distributed/microservice systems:
    • Cost of storing session data for millions of users.
    • Replication/sync latency across regions/servers.
  • Formalized ~2015. Stateless mechanism for transferring claims between parties.
  • Structure: header.payload.signature (base64-encoded, dot-separated)
PartContains
HeaderMetadata — signing algorithm used
PayloadClaims — sub (user ID), iat (issued-at time), plus optional fields like name, role
SignatureGenerated using a secret key; verifies integrity/tamper-proofing

flowchart LR
    A["Header
alg, type"] --> D["."]
    B["Payload
sub, iat, role, name"] --> D
    C["Signature
HMAC/RSA of header+payload with secret"] --> D

Advantages of JWT:

  • Statelessness → no server-side storage needed to verify identity.
  • Scalability → works great across microservices; any server with the shared secret can verify the token independently (no shared session store needed).
  • Portability → compact, URL-safe, can go in headers, cookies, or query params.

Disadvantages of JWT:

  • No revocation mechanism — a token is valid until it expires; can't kill it early without changing the server secret (which logs out everyone).
  • Token theft = impersonation — whoever holds the JWT can act as that user, with no built-in way to check it's "still legitimate" mid-lifetime.

Hybrid approach (mitigation): Keep JWT verification stateless, but maintain a blacklist in persistent storage (DB/Redis) for revoked tokens — checked in addition to signature verification. (Trade-off: this reintroduces a storage lookup, partially defeating the "pure stateless" benefit — a common interview discussion point.)

Practical advice from the video: for production systems, prefer a mature auth provider (Auth0, Clerk, etc.) unless you're very confident in your own implementation. Build your own only to learn.

C. Cookies

  • A way for the server to store a piece of data in the client's browser.
  • Browser security model: a cookie set by one server/domain is only sent back to that same server — not visible to other servers.
  • Typical usage in auth: server sets a cookie containing the session ID or JWT after successful login → browser auto-attaches it to every subsequent request to that server.
  • HTTP-only cookies: cannot be accessed via JavaScript (mitigates XSS token theft).

4. Types of Authentication

4.1 Stateful Authentication

%%{init: {'theme':'dark'}}%%
sequenceDiagram
    participant C as Client (Browser)
    participant S as Server
    participant R as Redis/DB (Session Store)

    C->>S: username + password
    S->>S: Validate credentials
    S->>R: Store session ID + user data
    S-->>C: Set-Cookie: sessionId (HTTP-only)
    Note over C,S: Subsequent requests
    C->>S: Request + Cookie(sessionId)
    S->>R: Look up sessionId
    R-->>S: User data / validity
    S-->>C: Authorized response
  • Session ID can be a random cryptographic string or even a JWT — implementation detail.
  • Pros: centralized control, real-time visibility into active sessions, easy to revoke/log out a user instantly.
  • Cons: limited horizontal scalability, operational complexity in distributed/multi-region systems (replication latency).

4.2 Stateless Authentication (JWT-based)

%%{init: {'theme':'dark'}}%%
sequenceDiagram
    participant C as Client
    participant S as Server

    C->>S: username + password
    S->>S: Validate credentials
    S->>S: Sign JWT with secret key (user ID, role, etc.)
    S-->>C: JWT token
    Note over C,S: Subsequent requests
    C->>S: Authorization: Bearer JWT
    S->>S: Verify signature with secret key
    S-->>C: Authorized response (or 401/403)
  • Pros: scalability, no session-store dependency, ideal for distributed systems and mobile apps (no cookies needed).
  • Cons: revocation is hard; token theft = impersonation until expiry.

4.3 API Key–Based Authentication

  • Use case: machine-to-machine (M2M) communication — no human/UI involved.
  • Example: your backend calling OpenAI's API programmatically instead of using the ChatGPT UI.
  • Workflow: generate a key in a dashboard → store it securely (env variable/secrets manager) → attach to each request (commonly a header) → identifies caller, quota, plan, permissions.
  • Ideal for: server-to-server calls, programmatic/automated access, single-purpose API clients.
  • Advantage: simple to generate and use; no login/session dance needed.

4.4 OAuth 2.0 / OpenID Connect (OIDC)

The problem OAuth solves: Delegation

  • One platform needs access to another platform's resources on a user's behalf (e.g., a travel app reading your Gmail for flight tickets, a social app importing your Google contacts).
  • Bad old solution: sharing your actual password → no way to limit scope, no way to revoke without changing password everywhere.

OAuth 1.0 (2007) — solved delegation via tokens (not passwords)

Key roles:

RoleDescriptionExample
Resource OwnerThe user who owns the dataYou
ClientThe app requesting accessFacebook
Resource ServerWhere the data livesGoogle
Authorization ServerIssues the tokenGoogle's auth server
%%{init: {'theme':'dark'}}%%
sequenceDiagram
    participant U as User (Resource Owner)
    participant C as Client (e.g. Facebook)
    participant AS as Authorization Server (Google)
    participant RS as Resource Server (Google Contacts)

    C->>AS: Redirect user to authorize
    U->>AS: Login + grant permission
    AS-->>C: Token
    C->>RS: Access resource using token
    RS-->>C: Contacts data

Limitation: cryptographic-signature-based, complex to implement correctly → error-prone.

OAuth 2.0 (~2010) — simplification

  • Introduced bearer tokens (simpler, but relies more on transport security like HTTPS).
  • Introduced multiple flows for different app types:
FlowUse case
Authorization Code FlowServer-side web apps
Implicit FlowBrowser-based apps (now discouraged — security risks)
Client Credentials FlowMachine-to-machine (no user involved)
Device Code FlowInput-constrained devices (e.g., Smart TVs)
Important: OAuth 2.0 solves authorization (delegation), NOT authentication. It doesn't inherently answer "who is this user" in a standard way.

OpenID Connect (OIDC, ~2014) — adds authentication on top of OAuth 2.0

  • Introduces the ID Token — a JWT containing user identity info (user ID, issued-at, issuer, name, email, etc.).
  • This is the tech behind "Sign in with Google/Facebook/Discord."
%%{init: {'theme':'dark'}}%%
sequenceDiagram
    participant U as User
    participant C as Client (e.g. Notes App)
    participant AS as Authorization Server (Google)

    U->>C: Click "Sign in with Google"
    C->>AS: Redirect to Google login
    U->>AS: Login + grant permissions
    AS-->>C: Authorization Code (+ optional ID Token)
    C->>AS: Exchange code for Access Token + ID Token
    AS-->>C: Access Token (JWT) + ID Token (JWT)
    C->>C: Decode ID Token to get user identity
    Note over C: Client can now call Google APIs
on user's behalf using Access Token
  • ID Token → answers "who is this user" (authentication).
  • Access Token → answers "what can the client do on the user's behalf" (authorization/delegation).

5. When to Use Which Authentication Type (Quick Decision Guide)

TypeBest for
Stateful (session-based)Traditional web apps / SaaS with server-rendered or single-domain apps; need real-time revocation & session visibility
Stateless (JWT)APIs, distributed/microservice systems, mobile apps (no cookies)
API KeyServer-to-server / machine-to-machine / programmatic single-purpose API access
OAuth 2.0 / OIDCThird-party login ("Sign in with X") and delegated access to another platform's resources
Real-world nuance: many systems use a hybrid approach — stateful sessions/cookies for the main web app (browser clients), stateless JWTs for mobile apps/third-party API integrations.

6. Authorization Deep Dive

RBAC — Role-Based Access Control

  • Users are assigned roles (e.g., user, admin, moderator).
  • Each role has a defined set of permissions on specific resources (read/write/delete).
  • Can be as granular as needed (different roles have different permissions on different resource types).
%%{init: {'theme':'dark'}}%%
flowchart TD
    A["User Signs Up"] --> B["Server assigns Role
e.g. user / admin"]
    B --> C["Subsequent Request
with Session ID / JWT"]
    C --> D["Server deduces Role
from token or DB lookup"]
    D --> E{"Role has permission
for this resource?"}
    E -->|Yes| F["Allow — proceed with request"]
    E -->|No| G["403 Forbidden"]
  • Example: a notes app's "Dead Zone" (soft-deleted notes) may only be accessible to admin role, not regular user role.
  • Anti-pattern to avoid: hardcoding a secret "god-mode" string sent with API calls to grant special access — insecure (leak = full compromise) and unscalable (hard to share/manage/revoke per person). RBAC solves this properly via structured roles/permissions.

7. Security Best Practices for Auth Flows (commonly asked in interviews)

7.1 Generic Error Messages

  • Never reveal specific reasons for auth failure:
    • ❌ "User not found"
    • ❌ "Incorrect password"
    • ❌ "Account locked due to too many attempts"
  • Why: each of these gives an attacker a clue (e.g., confirms a username exists, letting them focus brute-force efforts on the password).
  • ✅ Always return a generic message, e.g., "Authentication failed", regardless of which step failed.

7.2 Timing Attacks

  • Typical auth flow order: (1) find user → (2) check if locked → (3) hash & compare password.
  • Problem: if the username doesn't exist, the request fails fast (step 1). If the username exists but the password is wrong, it fails later (step 3, after a hashing operation) — hashing takes measurably longer.
  • This time difference is a side-channel — attackers can measure response time to infer whether a username is valid, even with generic error messages.
  • Mitigations:
    1. Constant-time comparison functions for password/hash comparison (execution time independent of input similarity).
    2. Simulate artificial delay (e.g., setTimeout in Node, time.sleep in Go) on the fast-fail path so all responses take roughly the same time regardless of which step failed.

8. Key Interview Takeaways

  • AuthN = who you are; AuthZ = what you can do. Always in that order.
  • HTTP is stateless by design — sessions were introduced to add memory/continuity for the client.
  • Sessions vs JWT is fundamentally a stateful vs stateless trade-off:
    • Sessions → server-side lookup required, easy revocation, harder to scale across distributed systems.
    • JWT → self-contained, no lookup needed, scales well, but revocation is the classic pain point.
  • Hybrid JWT + blacklist is a common real-world compromise — know the trade-off it reintroduces (a storage lookup).
  • Cookies are the delivery mechanism for both session IDs and JWTs in browser-based apps; use HttpOnly to block JS access (XSS mitigation).
  • API keys are for machine-to-machine access, not user-facing login.
  • OAuth solves delegation (accessing another platform's resources without sharing your password) — it does not solve authentication by itself.
  • OpenID Connect (OIDC) = OAuth 2.0 + ID Token (JWT) — this is what "Sign in with Google" actually uses; it adds identity/authentication on top of OAuth's authorization/delegation model.
  • OAuth 2.0 roles: Resource Owner (user), Client (requesting app), Resource Server (holds data), Authorization Server (issues tokens).
  • OAuth 2.0 flows: Authorization Code (server apps), Implicit (deprecated, browser apps), Client Credentials (M2M), Device Code (input-constrained devices, e.g., Smart TVs).
  • RBAC is the standard authorization model: roles → permissions → resources.
  • Never leak auth-failure specifics in error messages — always generic ("Authentication failed").
  • Timing attacks are a real, often-overlooked vulnerability — mitigate with constant-time comparisons or simulated delays.
  • Practical advice: build your own auth to learn, but use a managed provider (Auth0, Clerk, etc.) in production unless you're very confident in your security implementation.

9. Possible Interview Questions to Prepare For

  1. What's the difference between authentication and authorization?
  2. Why is HTTP stateless, and how do sessions solve that?
  3. Compare stateful (session) vs stateless (JWT) authentication — pros, cons, and when to use each.
  4. What are the three parts of a JWT? What's stored in each?
  5. Why is revoking a JWT hard? How would you design around it (hybrid blacklist approach)?
  6. What problem does OAuth solve? Why couldn't we just share passwords?
  7. What are the four roles in OAuth 2.0?
  8. What's the difference between OAuth 2.0 and OpenID Connect? Why was OIDC needed on top of OAuth?
  9. List OAuth 2.0's grant flows and when each is used (auth code, implicit, client credentials, device code).
  10. What is RBAC, and how would you design a permission system for a multi-tenant app?
  11. Why should authentication error messages be generic instead of specific?
  12. What is a timing attack in the context of login, and how do you defend against it?
  13. When would you use API key authentication instead of OAuth or JWT?
  14. What's an HTTP-only cookie, and why does it matter for session/token security?
